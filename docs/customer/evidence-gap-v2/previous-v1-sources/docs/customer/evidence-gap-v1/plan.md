# 证据缺口分流 V1

2026-11-01。目标：让客服明确区分用户条件未说明、项目事实未核实和核验服务不可用；避免把资料不足变成画像问卷，或把用户接受探索当成项目能力已被证明。

## 决策约定

| 情况 | 处理 | 不改变的事实边界 |
|---|---|---|
| 当前任务确有用途、运行环境、使用方式或条件歧义 | 复用任务内唯一开放问题，状态 USER_INPUT_REQUIRED | 只收集用户本人的条件；已确认、已跳过的条件不补问 |
| 用户需求已清楚，但候选的功能、依赖、资源或许可无依据 | PROJECT_FACTS_UNVERIFIED，列出待核实项 | 不要求用户替系统确认项目事实，不自动放宽条件 |
| 有些答案有原文支持，还有些项目事实缺失 | PARTIALLY_SUPPORTED_EXTRACTS，分别显示已核对内容与缺口 | 不把“每条引用真实”当成“整个问题已经回答” |
| 用户愿意先考察未完全核实的项目 | USER_DECISION_REQUIRED / ASK_PREFERENCE | 这是探索取舍；UNKNOWN 和禁止导入保持原规则，不能变成 SATISFIED |
| 两种缺口同时存在 | MIXED_GAPS，分别列出；本轮最多一个真实用户问题 | 补充用户条件不会清空未知项目事实 |
| 服务超时、Embedding 或事实核验失败 | VERIFICATION_UNAVAILABLE，条件保留，恢复后核验 | 不假称无合适项目，不要求用户因此修改条件 |
| 已检查候选确无符合项、且没有未完成核验项 | NO_VERIFIED_CANDIDATE，明确只限本轮覆盖范围 | 不推断整个 GitHub 没有合适项目 |

用户问题来源是现有权威任务 question / pendingConditions；事实缺口来源是本轮已验证引用后的覆盖判定、逐项 requirementMatches 或严格模式移除前保存的 verificationGaps。新增 `evidenceDecision` 统一暴露来源和下一动作，不直接采信模型自报的 USER_INPUT 标签。

纯事实问答不会重新显示旧推荐问题，但旧问题仍保留在原任务中，未自动回答、取消或迁移。个人适配／推荐缺少用户环境时仍走现有 COLLECT 与任务追问流程；本轮不新增另一套独立 QA 任务和问答恢复协议。

## 问答覆盖核验

复用已有 VERIFY 模型调用，增加当前 question，不增加一个新的模型调用阶段。无 question 的项目推荐事实核验保持 supportedIds 协议。QA 输出为：

```json
{"supportedIds":[0],"coverage":"COMPLETE|PARTIAL|INSUFFICIENT","missingFacts":[{"questionQuote":"问题中的连续原话","reason":"尚缺的项目事实"}]}
```

服务端验证缺口的数量、长度和原话锚点。缺口最多6项，不接受用户问卷、伪造问题原话或未知字段；旧协议、非法覆盖信息降为 UNASSESSED。没有已支持引用时不能 COMPLETE；有缺口却声称 COMPLETE 时降为 PARTIAL。

INSUFFICIENT 不展示无关但真实的摘录作为答案；PARTIAL 只显示已核对的片段并明确缺口；缺少覆盖信息不会假装已完整回答。排障堆大小不能证明最低机器内存，平台可扩展不能证明现成业务功能，开源协议不能证明某商业版功能免费。

## 短事实和预算

保留 B 检索接口的既有粗筛协议，客服可以把非空、非纯导航的短片段继续送入引用与覆盖核验；不能仅因短于500字或不足2个章节拒绝版本、许可等短事实。该变化只针对客服入口，不修改管理端 RAG 回答预览的协议。

短引用只通过服务端 spanId 恢复原文，仍核对原文包含关系并经过模型事实核验；旧的自由 quote 输入保持20字下限。纯标题、纯图片和纯导航仍排除。VERIFY 的实际输入预算现在包含 QA question；保留既有阶段超时、输出预算和取消规则。短片段过去可能只检索就结束，现在可能继续进入原有生成与核验阶段，不能据此宣称成本或延迟不变。

## 接入与展示

- `CustomerEvidenceCoverage`：独立校验问题覆盖及项目事实缺口。
- `CustomerEvidenceDecision`：统一用户输入、用户取舍、项目事实、服务失败和候选覆盖分类。
- `CustomerEvidenceSteps`：QA入口、部分回答、不可用回退、短事实放行。
- `CustomerRequirementMatcher`：严格模式移除未知候选前保留事实缺口。
- `CustomerTaskService`：纯事实插问不展示旧追问；服务不可用时不新建取舍问题。
- `CustomerConversation`：在任务收尾后记录实际追问和 evidenceDecision 审计事件，两个执行器复用相同逻辑。
- 客服页面：推荐结果或严格模式空列表可以显示具体待核实项目事实，已有追问区域继续显示用户问题。

## 验收

测试真实 Java 状态机、原文恢复、模型边界的严格解析和真实 LangGraph4j 路由，模型输出使用可控测试替身。覆盖完整／部分／无关回答、旧协议缺覆盖、短版本／许可、用户用途／部署环境澄清、旧追问隔离、严格模式缺口保留、接受探索不解锁导入、服务失败不反问。

保存模拟回复、源码快照和测试报告，并只读复验前序分类、分块和排序证据。此轮外部模型、Embedding调用为0，不升级数据库、不切换知识索引、不启动网站后台。语义模型能否稳定产生新的覆盖判定仍需单独真实验收，离线通过不能解释为真实客服回答正确率。
