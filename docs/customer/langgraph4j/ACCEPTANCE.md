所有运行都在 90 秒内进入终态，并不等于用户问题全部解决。Embedding 429、读取超时、工具池拒绝导致部分推荐降级为业务资料候选。多数证据链没有走完，不能用这一组耗时推导框架使正常 RAG 更快，也不能从仅多通过一题宣称质量提升。

- G15：平台政策知识问题，双方两轮均发生 KNOWLEDGE_UNAVAILABLE。
- G16：知识库中 RAG 项目功能问题，双方两轮均进入 CHAT / CONVERSATION，未满足冻结的 QUESTION 预期。这是共同的意图理解问题，未在本次改写 Prompt 规避。
- G14：两次把库存管理记录为 topic，而预期要求 goal。存在合理语义分类争议，需人工判定；没有在看到结果后改测试提高通过率。
- G11：旧编排第二轮用途核对不可用。诊断显示工具资源拒绝等依赖问题，不能归因于图框架。

代码核查发现原实现的 `KNOWN_EVIDENCE_SUFFICIENT`（25 字符）超过 customer_step.status 的 VARCHAR(24)，与四次用途核对 DataIntegrityViolationException 高度对应。本轮已缩短为 `KNOWN_EVIDENCE_READY`，真实 MySQL 测试复现旧值失败并确认新值可写入。80 轮报告保留修复前实测值；**没有声称修复后重新跑过 80 轮**。

独立对照后还修复了共享步骤提取时选择候选的异常恢复边界，保持冻结原实现的处理语义，确定性回归已覆盖。模型、Prompt、检索策略不变。provider-compiled-manifest.json 记录真实测试当时编译类哈希，最终源码包含上述修复和后续观测计时优化。

## 性能失败及修复记录

初次固定响应测量差值 83 ms。为增加图创建和检查点细分耗时，一度每次检查点额外写一条计时记录，复测差值上升为 888 ms，未通过。失败记录保存在 `overhead-per-checkpoint-writes.json` 和 `persistence-per-checkpoint-writes.log`。

最终改为在本轮账本中累计计时，随正式结果保存，不额外逐次写库。检查点仍逐节点写入、失败仍停止图执行。最终 100 轮/引擎、2 并发复测差值 75 ms，通过 200 ms 目标；连接池活动连接归零。

- 最长合法会话及最大卡片、服务器负载、SSE 代理、部署切换、两级回退演练及至少 24 小时观察。
