# 项目客服对话与界面改进

2026-10-03，按“参考 Harness 界面与记忆机制、保留 Java 平台”的选择实施。

## 行为

- 所有正常输入先调用客服配置模型 `deepseek-flash`，问候、感谢、闲聊和通用技术解释使用 CHAT 动作中的模型回复，不要求检索项目证据，不使用固定欢迎词替代模型。
- 模型输入包含已确认账号画像、当前条件、近期历史和历史摘要。当前明确修改优先，画像仅补充未指定条件；临时条件不自动写回画像工坊。
- 用户明确要求推荐立即执行真实项目查询，缺少画像不作为推荐前置门槛；目标未知时查询学习与求职两类已发布项目。推荐后可以补问一项偏好。
- 已展示候选后的条件修改继续检索；硬条件仍由服务端执行，缺失字段不能推断为满足。具体项目身份和证据仍通过原有校验与导入防线。
- 闲聊自然回应，适时引导，避免每轮重复追问；模型不能通过 CHAT 伪造项目链接或证据编号。
- 原生动作返回无法解析时，仅一次 JSON 输出模式重试；与供应商重试共享最多两次尝试，受剩余期限约束。两次都计入用量，条件校验失败不会被当成格式错误重试。

## 记忆与界面

独立入口 `/customer`，左侧导航“项目客服”。移除趋势页的“自由提问”页签；趋势推荐及工作能力参考仍保留。支持新建会话、历史、来源、进度、停止和刷新恢复。

保留 MySQL 原始消息与结构化条件，模型只接收有预算的视图，优先裁剪早期历史，不发送庞大的条件来源记录。已有摘要机制继续使用；没有移植 Harness 完整压缩运行时或引入新的会话存储。

客服界面不再展示模型名称、思考模式、Token 或费用。后台继续保留整轮调用用量和成本记录，支持评测与审计；本次界面调整不改变模型或费用统计逻辑。

### 已核实的问题与处理

| 原问题 | 本次处理 | 边界 |
|---|---|---|
| 模型已理解周期，Java 正则不认识原话导致整轮失败 | 模型输出数量、单位、AT_MOST/AT_LEAST；Java 负责单位换算、范围、原文依据和已知冲突检查 | 月仍按项目估算30天；工作日需要用户澄清，未实现节假日日历 |
| 条件错误与聊天绑在一起 | 各字段独立接纳；不确定项持久化、显示并追问 | 不能承诺任意语义正确，不能把无法确认的限制当作已满足 |
| 上限和下限混淆 | 新增最短周期，支持上下限并检查冲突；半年内包含两个月 | 项目估计区间需整体落在要求内；未知周期是待核实 |
| 资料缺失与明确冲突都被排除 | 区分确认匹配、待核实候选、明确冲突；待核实候选带conditionGaps | 明确冲突和下架项目不展示；待核实候选不允许导入正式方案 |
| B或证据生成出错导致真实项目卡片消失 | 保留业务库身份和已记录事实，引用清空，关闭导入，说明资料核对未完成 | 实际错误仍记入步骤；不回退A，不编造证据 |
| 可选证据步骤耗尽整轮期限 | 为项目结果保存预留5秒；证据不能按时完成时降级 | 真正的取消、整轮超时、权限失效仍终止执行 |
| 普通聊天展示和失败提示僵硬 | 模型自然回复、安全Markdown、错误引用标记移除；各种终态都有可继续的说明 | 供应商故障仍保留真实FAILED等状态，不伪造生成成功 |

## 2026-10-03：v4.1 推荐排序、证据范围与连续对话

版本：`customer-v4.1-scoped-evidence`。在v4语义处理基础上继续改进，没有更换模型、B索引代际或A入口，也不需要数据库迁移。

### 实现变化

1. **推荐先召回，再筛选排序。** 根据已确认的语言、主题、目标和基础执行B混合检索，最多20个片段。业务库负责项目身份、发布状态和条件检查。排序先按待核实条件数量升序，再综合语义来源排名、质量分和明确新手偏好，最多展示3个项目。初始分数为`70/sqrt(去重来源名次) + clamp(质量分,0,100)*0.15 + 新手匹配15`，只用于排序，不能绕过硬条件。该权重尚未经过独立业务集标定，不等于已经证明效果最优。
2. **先限定项目文档，再召回说明证据。** 根据项目业务标识和仓库名定位READY、未删除、有有效版本的文档；业务介绍优先保留。向量、词法和名称路线都在截断前加入documentId范围，最后最多8个片段。缺少对应文档就返回资料不足，不能扩大为全库检索。已有Redis numeric documentId字段可复用，无需重建索引。
3. **证据预算按项目分配。** 同项目的业务介绍和README共享预算，每项目最多3个片段，轮流分配；上下文超限时缩短各项目片段，而不是不断删掉末尾项目。最终仍检查引用来源和事实支持，没有通过验证的项目不能导入方案。此机制不能保证每个项目都被召回或生成引用。
4. **召回异常可解释。** 语义检索异常时保留业务条件、基础偏好和质量排序，页面展示降级原因；资料核对失败时保留有效项目身份和已记录事实，不生成虚假证据，不回退A。
5. **指代与追问。** 保存最近明确追问，模型可据此理解“刚学”“半年以内”等简短回答。详情和比较后，以实际展示顺序保存候选列表；修复“比较第一个和第三个”只提取第一个的规则错误。生成途中项目下架时移除该项目并关闭剩余卡片导入，避免证据状态不一致。
6. **工具限制保持。** 通常推荐为画像、相关性召回、业务项目查询、限定证据检索，共4个工具步骤、2次知识检索。重复片段可作为本轮说明依据，不误判为整轮失败；总工具次数和检索次数上限仍生效。

### 真实状态解释、确认与耗时

- STATE和DIAGNOSE作为独立意图；常见条件查询、原因查询、单独确认由确定性路由处理。回答来自状态差异或实际数量计算，忽略模型可能猜测的系统原因。模型合成测试中DIAGNOSE的自由reply仍有推测，这证明不能仅靠提示词；该reply不会用于用户回答。
- 每轮记录接受后的条件变化；60→180明确显示，不再统一说“条件未放宽”。没有difficulty时，取消难度正常返回“本来没有限制”，保留experience。
- 支持SET/CLEAR语义；询问是否取消时保存有来源原话的操作与期望旧值。明确确认只执行唯一、仍适用的已保存操作；取消确认保留原条件。旧待确认项中的明确取消原话可恢复处理；不把“确认”覆盖成新的条件原话，也不猜测无法归一化的值。
