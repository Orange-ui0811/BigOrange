## 已修复问题 LIVE-BUG-01

CustomerTaskService.operation 原先优先匹配“先记录/不要搜索”，覆盖了模型提出且有原话依据的 SWITCH_TASK/RESUME_TASK，导致新目标覆盖旧任务且恢复失效。现在先校验明确任务控制，再独立执行“不搜索”的要求；恢复目标不明确时保留澄清提示。

新增 CustomerCompositeTaskControlTest 3 项。修复后完整相关回归 **510 项：487 通过、23 条件跳过、0 失败/错误**。23 跳过项包含先前已单独通过的 4 项 MySQL 集成；没有重复相加成新用例。修复不涉及来源仓储 SQL，因此没有重复运行相同数据库套件。

失败会话 576 与原始轮次保留；修复后另建会话 579 复测，不能通过改写失败历史制造通过。

## 仍需修改

### LIVE-QUALITY-01：初学者适配没有形成有效排序依据

Java 被结构化核验，但“初学者练习”仅保存为 SOFT/UNKNOWN。引用自身已经说明 Nacos 需要扎实分布式与 Java 功底，Doris 项目庞大、学习曲线陡峭，却仍排在前面。

下一步应保留用户基础为偏好的既定语义，增加可追溯的基础归一化与学习适配排序/解释，不能偷偷把基础改成专区或难度硬筛选。若缺少适配依据，需要明确说明未知，而不是呈现为已证明适合初学者。

### LIVE-QUALITY-02：具体业务用途被通用搭建工具替代

库存请求里的商品、采购、销售、库存功能被保存为软目标。用途模型将 ToolJet 的“内部工具、工作流、可视化构建器”判断为 SUBTOPIC；需求匹配中这些业务能力均 UNKNOWN，但没有硬条件冲突就获得 VERIFIED_PROJECTS。

需要将“用途相关”“核心业务能力满足”“用户约束满足”“偏好适配”分开验证。具体业务功能没有依据时不能给出已核实满足标签；构建平台可以作为明确标注的搭建路线备选，不能等同于已经具备进销存功能的项目。仅继续改写提示词不能替代服务端结果门槛。

建议下一轮优先修这两个问题及其回归，再改进候选补查和 GitHub 扩展；扩大召回本身不能解决错误放行。
