# 客服追问与下一步动作规则

状态：第一阶段目标规范；使用 [状态契约](02-state-contract.md)。设计参数不是经过生产评测的最优阈值。

## 准备度不是画像完整度

能描述用户想解决的主要问题，且不存在会改变关键筛选方向的歧义，即可试搜。基础、语言、时间并非每个任务必填；“帮我整理需求，先别找”优先于准备度。

例如“Java 求职项目”可以问目标岗位或经验中更影响选项的一项；“给小店找库存系统，接受少量改造，日常必须离线”已经可以探索，不应继续强制问学历和求职方向。

## 决策顺序

| 顺序 | 判断 | 动作 |
| --- | --- | --- |
| 1 | 取消、暂停、只记录、明确操作等用户控制请求 | 先执行对应状态规则；不偷偷推荐 |
| 2 | 操作对象、所属任务或关键指代不明确 | CLARIFY_REFERENCE，停止依赖该对象的动作 |
| 3 | 用户表达有关键歧义或有效硬要求冲突 | ASK_REQUIREMENT，问题限定到矛盾处 |
| 4 | 没有搜索依据或用途不清楚 | ASK_REQUIREMENT，问一个能改变选择的问题 |
| 5 | 能搜索，缺少候选 | SEARCH_LOCAL |
| 6 | 有候选，缺少可核实的项目事实 | FETCH_EVIDENCE；无法补齐则保留 UNKNOWN |
| 7 | 候选差异需要用户取舍 | ASK_TRADEOFF；若用户要求先看，转 PRESENT |
| 8 | 已有可解释候选 | PRESENT；不要求画像全满 |
| 9 | 已知冲突、覆盖不足、服务故障或执行预算结束 | 按下表分别处理，不共用“请降低要求” |

一轮可以经过若干只读步骤，但最多发布一个主要追问。每次工具循环须说明新信息目标。上述顺序不意味着每个请求都要执行每一行。

## 问什么

问题记录 askedReason：哪个不确定性影响哪类候选，以及回答后准备改变什么。优先：硬要求歧义 > 重要用途/取舍 > 可选偏好。并列时选用户更容易回答且未问过的问题。

- 候选主要分成成品应用和框架：问直接部署还是接受改造。
- Java 求职候选难度跨度大：问已做过哪些项目，比机械询问“入门/进阶”更容易理解。
- 项目是否支持离线未知：查依赖和部署资料，不向用户追问“你确定要离线吗”。
- 把选项作为帮助，不限定合法答案；用户一次给出多个方面应全部保留。
- 保留 skipReason；没有新的重要原因不重复问同义问题。硬要求歧义未解决且用户跳过时，明确筛选受限，可展示标为不完整筛选的探索候选，不能宣称合格。

## 停止与无进展

满足以下任一条件时停止主动补问：已有足够依据展示可比较候选；用户明确先看；用户不愿继续；连续相似问题没有新增信息。必要指代和写操作参数仍须明确。

“停止补问”不表示编造答案。可以输出当前需求、已知候选、未知项及可选下一步。两三轮可以作为后续体验监测点，不作为必须填满或绝对封顶的业务规则。

每次补查比较新的来源 ID、事实、候选和已解决歧义。相同查询/范围/资料版本重复且无新信息时不再循环。具体工具次数、超时沿用当前配置，新增 GitHub 前另行评估，不能凭设计放大现有预算。

## 四种不足与有限扩展

| outcome | 判定依据 | 行为 |
| --- | --- | --- |
| NO_MATCH | 已核对的本次范围内候选均与硬要求冲突 | 说明冲突和已查范围；可提出调整选项，但不自动放宽 |
| COVERAGE_GAP | 本地缺对应主题/类别资料，或合理查询变体后发现覆盖缺口 | 在预算允许且工具可用时 SEARCH_GITHUB；否则说明当前范围限制 |
| EVIDENCE_INCOMPLETE | 已有相关候选，但关键事实未知 | 定向补查；探索模式标未知，严格模式排除未核实候选 |
| SERVICE_UNAVAILABLE | 超时、限流、连接/模型失败 | 保留需求，报告阶段失败；可以给仍有效的既有结果，不伪装新搜索成功 |

零命中先检查查询、过滤条件、索引/服务健康；不能直接推出 NO_MATCH 或 COVERAGE_GAP。只有失败状态不足以把 GitHub 作为静默替代。用户明确要求扩大搜索时可执行，但要注明范围和本地故障。

GitHub 候选仍需规范身份、读取资料、逐项匹配和证据校验；搜索排序不等于适配排序。扩展不能保证找到项目；扩大范围并不允许放宽硬要求。预算耗尽返回 LIMIT_REACHED，与 NO_MATCH 分开。

## 最终输出

对每个候选展示：身份、适合原因、需求匹配摘要、未知项、来源、是否待考察，以及查看/比较/更换等下一步。展示和导入资格分别校验。明确选定才完成选择任务，导入由 ACTION 路线单独返回回执。

输出 status 建议采用 ANSWERED、NEEDS_CLARIFICATION、RECOMMENDATIONS、NO_MATCH、COVERAGE_GAP、EVIDENCE_INCOMPLETE、SERVICE_UNAVAILABLE、LIMIT_REACHED、STATE_RECORDED、ACTION_SUCCEEDED、ACTION_FAILED。任务状态、问题状态与这些结果状态分开。

## 模型与程序边界

模型提出意图、关联、需求与问题建议；程序校验原话、身份、当前版本、必经步骤、工具白名单和结果引用。没有工具结果不能声称已搜索，没有回执不能声称已导入。历史摘要不能创建授权或覆盖当前确认需求。

第一阶段仅通过合成输入与预期输出检查这些规则；模型语义准确率、追问收益、真实搜索覆盖率和实际成本属于下一阶段评测。
