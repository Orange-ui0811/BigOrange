## 当前代码基线

2026-10-29 已重新读取源码，未运行服务或 Java 测试。

- `CustomerState` 当前有 CHAT、QUESTION、COLLECT、RECOMMEND、DETAIL、COMPARE、STATE、DIAGNOSE、EXPLAIN；条件字段固定，另有自由偏好与待澄清项。
- `CustomerConversation.branch()` 负责当前分流，`followUp()` 主要补问目标、基础、方向。
- `CustomerTurnPlan.resolve()` 已能解析明确列表位置、关注项目及部分指代，但在理解与状态协调后执行；本设计将关联检查前置，保留服务端身份校验。
- `CustomerTaskProgress` 保存 runId、phase、status、topic，是运行进度，不是完整多轮任务契约。
- `CustomerGraphState` 明确是诊断状态；不能将现有检查点称为任意节点可恢复执行。
- Mewhelp 的 `app/graph/routing.py` 将九类意图映射到五条路线；借鉴统一映射与固定前置步骤，不照搬电商意图、未知意图的默认业务出口或全量工具绑定。

源码路径与后续改造位置见 [实现映射](04-implementation-map.md)。

## 公共入口

```text
登录及会话归属校验 → 请求去重 → 加载任务、待回答项、候选列表和必要历史
→ 指代消解与任务关联 → 意图和对话动作提取 → 校验需求变更
→ 路由并执行工作流 → 按结果类型校验 → 原子保存状态与回复 → 本轮结束
```

### 指代消解

1. 优先处理可信的 questionId、项目选择、列表 ID 与位置；即使来自前端也须校验会话归属和版本。
2. 对“第二个”绑定明确候选列表；对“Java”结合开放问题判断；对“继续”读取未完成任务。
3. 程序无法确定时，模型可提出关联建议，但不得生成权威 projectId。服务端验证 ID、来源与关系。
4. 若歧义会影响操作、需求变更或检索范围，返回 DIRECT/CLARIFY_REFERENCE，不猜选。可以先理解消息，但不得沿含糊对象执行业务。
5. 保存原话、补全问句、对象引用、来源消息、消解状态。补全问句不能成为新增硬要求的原话证据。
6. 可将语义消解与意图提取合为一次模型调用；逻辑顺序与权限校验不变。

## 八类意图与六条路线

| 意图 | 路线 | 例子 |
| --- | --- | --- |
| CHAT | DIRECT | 你好；Redis 是什么 |
| UNKNOWN | DIRECT | 无法确定对象的“就那个吧” |
| KNOWLEDGE_QA | KNOWLEDGE | 根据平台资料说明部署要求 |
| FIND_PROJECT | RECOMMEND | 找个 Java 求职项目；换一个 |
| PROJECT_DETAIL | PROJECT_REVIEW | 第二个支持扫码吗 |
| COMPARE_PROJECTS | PROJECT_REVIEW | 比较前两个项目 |
| TASK_STATUS | INSPECT | 当前有哪些要求；刚才为什么失败 |
| PROJECT_ACTION | ACTION | 把选定项目加入我的项目 |

补充条件、取消条件、回答问题、排除候选、暂停和继续是对话动作，不再各自定义一套业务路线。

### DIRECT 直接交流与最小澄清

- 步骤：理解 → 回复或问一个定位问题 → 保存结束。
- 普通概念解释不调用项目或知识工具；明确要求资料依据时转 KNOWLEDGE。
- 可保存用户明确的需求变更；“只记录不推荐”不得启动搜索。
- UNKNOWN 不默认执行工具。未关联到唯一任务的要求不得写入任意旧任务。

### KNOWLEDGE 资料问答

- 步骤：明确对象和范围 → 检索 → 证据覆盖判断 → 必要补查 → 生成引用回答 → 校验。
- 白名单：知识检索、来源读取。具体项目指代优先转 PROJECT_REVIEW。
- 证据不足可部分回答并标注缺口；服务失败不能写成“没有相关知识”。
- 不自动修改用户偏好，不创建推荐任务，不把回答顺势变成推荐。

### RECOMMEND 需求驱动推荐

- 步骤：确认需求 → 准备度判断 → 库内候选发现 → 逐项匹配 → 问用户、补查或展示。
- 条件含糊影响筛选时先澄清；可探索时不等待所有画像填写完毕。
- GitHub 搜索仅作为覆盖不足时的扩展。现有数据、查询与返回是否成功应先检查；零结果不能独立证明覆盖不足。
- 库内冲突可解释并提供选择；用户明确要求继续寻找库外项目时可扩展。不得擅自放宽硬要求。
- 白名单：项目搜索、知识检索、项目详情；GitHub 搜索与资料获取为后续新增工具。
- 每次循环需获得新证据、减少关键歧义或改变候选；无进展及预算结束时输出已有结论并结束。

### PROJECT_REVIEW 指定项目核查与比较

- 步骤：确定项目身份 → 确定问题维度 → 限定项目获取资料 → 逐项核查/同维度比较 → 校验。
- 白名单：指定项目详情与相关证据；不进行无关全库搜索。
- 找不到唯一对象时澄清。资料未知与功能不存在不同；可改造与已实现不同。
- 用户要求更换时，显式转 RECOMMEND，并保留有效需求。

### INSPECT 状态与执行解释

- 步骤：读取需求、匹配记录、运行结果 → 解释 → 结束。
- 白名单：所属任务和运行记录。默认不重跑检索、不改变条件。
- 同轮“解释旧推荐并修改要求”：先根据变更前记录解释，再应用原话支持的新要求，执行明确请求的动作。

### ACTION 平台操作

- 步骤：确定具体操作和项目 → 归属、有效性、现有导入资格检查 → 必要选择/确认 → 幂等执行 → 返回回执。
- “不错”不是导入授权；明确的导入请求且参数齐全时不重复确认。
- 待考察候选的展示资格不自动授予导入资格；继续沿用现有服务的资格检查。
- 没有执行回执不得说导入成功。推荐任务完成与导入成功分别记录。

## 混合意图与跨轮规则

- 一轮最多一个有状态的主业务动作，可有一段只读解释；两个独立目标不可可靠定序时请用户选先做哪一个。
- 插入概念或事实问答不关闭原待回答问题，不自动把插问内容当作偏好。
- 用户明确暂停：任务 PAUSED，开放问题取消或失效；恢复时检查旧问题仍是否必要。
- 明确切换目标：暂停旧任务，新建新任务；不自动复制任务专属需求。明确“沿用上次时间限制”才按可追溯来源复制。
- 同会话可以保留多个历史/暂停任务，只有一个当前活动任务；“继续”关联不唯一时澄清。
- 选定明确项目或明确结束使任务 COMPLETED；返回候选只进入 PRESENTED。
- 模型判断把握、检索相似度、证据充分程度、项目适配度分别存储，不用单个 confidence 代替。
