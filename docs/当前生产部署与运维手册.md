# OrangeVC 当前生产部署与运维手册

> 文档版本：3.0  
> 最后更新：2026-08-14  
> 适用代码：`D:\Orangejd` 的 V3 分支当前版本  
> 适用生产站点：`https://orangevf.com`  
> 用途：生产发布、日常巡检、故障定位、备份恢复和安全复审的唯一操作手册

## 1. 运维原则

1. 生产品牌是 **OrangeVC**，`orangevf.com` 是唯一规范域名；内部历史名称 `orangejd` 继续用于目录、服务名和包名。
2. 生产服务器不执行 `git pull`，不从本地目录零散复制文件。唯一标准发布物由 `scripts/build-release.sh` 生成，服务器统一使用 `scripts/install-release.sh` 安装。
3. 秘密只保存在服务器受限文件中，不写入 Git、发布包、日志、聊天记录或截图：
   - 应用配置：`/etc/orangejd/orangejd.env`
   - 数据库备份配置：`/etc/orangejd/mysql-backup.env`
   - age 加密公钥：`/etc/orangejd/mysql-backup-recipient`
4. 日常发布只替换后端 JAR、用户端、管理端和 Nginx 站点配置，不清库、不清 Redis、不删除 OSS 或上传目录。
5. 数据库结构只由 Flyway 管理。已发布的迁移文件不可修改，新增结构必须创建更高版本迁移。
6. 任何会改变生产数据、环境变量、Nginx、证书或数据库的操作，必须先备份并记录操作时间。
7. 先执行只读诊断，再决定是否重启；不要用重启掩盖数据库、配置或资源问题。
8. 恢复公开写入后，旧数据库即开始落后，不能直接切回旧库。

## 3. 服务、定时器和责任边界

### 3.1 核心服务

| 单元 | 作用 | 是否应常驻 |
| --- | --- | --- |
| `orangejd.service` | OrangeVC 后端 | 是 |
| `nginx.service` | HTTPS、静态文件和反向代理 | 是 |
| `mysql.service` | 本地生产数据库 | 是 |
| `redis-server.service` | 缓存、会话和向量索引 | 是 |

后端以 `admin` 用户运行，JVM 当前限制为：

```text
-Xms512m -Xmx2048m -XX:MaxMetaspaceSize=384m
```

### 3.2 数据库运维定时器

| 定时器 | 频率 | 作用 |
| --- | --- | --- |
| `orangevc-mysql-backup.timer` | 每天 02:30，随机延迟最多 120 秒 | 完整导出、压缩、age 加密并上传 OSS |
| `orangevc-oss-backup-retention.timer` | 每周日 03:30，随机延迟最多 300 秒 | 按前缀清理过期 OSS 备份 |
| `orangevc-database-healthcheck.timer` | 开机 5 分钟后，之后每 15 分钟 | 检查 MySQL、应用、Nginx、备份和磁盘 |

检查是否启用：

```bash
systemctl list-timers --all | grep -E 'orangevc-(mysql-backup|oss-backup-retention|database-healthcheck)'
```

## 4. 日常只读巡检

以下操作不会修改生产状态，出现告警时应先执行。

### 4.1 一分钟总览

```bash
systemctl is-active orangejd nginx mysql redis-server
systemctl is-active orangevc-mysql-backup.timer orangevc-database-healthcheck.timer
curl -fsS http://127.0.0.1:8081/actuator/health
df -h /
free -h
```

正常结果：四个核心服务均为 `active`，Actuator 返回 `UP`，根磁盘低于 70%。

### 4.2 站点检查

```bash
curl -I https://orangevf.com/
curl -I https://orangevf.com/market
curl -I https://orangevf.com/admin/
curl -I https://orangevf.com/robots.txt
curl -I https://orangevf.com/sitemap.xml
curl -I https://orangevf.com/.well-known/security.txt
curl -I https://orangevf.com/assets/not-exist.js
```

预期：

- 首页、市场和管理端返回 `200`。
- HTTP、`www.orangevf.com` 统一 `301` 到 `https://orangevf.com`。
- `robots.txt` 为文本，`sitemap.xml` 为 XML，`security.txt` 为文本。
- 不存在的 `/assets/*` 和 `/admin/assets/*` 返回 `404`，不得回退到 SPA HTML。
- 页面响应包含 HSTS、CSP 和 `X-Content-Type-Options: nosniff`。

### 4.3 日志读取

```bash
sudo journalctl -u orangejd --since '30 minutes ago' --no-pager -l
sudo journalctl -u nginx --since '30 minutes ago' --no-pager -l
sudo journalctl -u mysql --since '30 minutes ago' --no-pager -l
sudo journalctl -u orangevc-database-healthcheck --since '24 hours ago' --no-pager -l
sudo tail -n 100 /var/log/nginx/error.log
sudo tail -n 100 /var/log/mysql/mysql-slow.log
```

分享日志前必须遮盖 Token、邮箱、手机号、URL 查询参数和外部服务响应中的敏感内容。

## 5. 生产环境变量

### 5.1 查看与编辑

只查看变量名，不输出值：

```bash
sudo awk -F= '/^[A-Z0-9_]+=/ {print $1}' /etc/orangejd/orangejd.env | sort
```

编辑前创建受限备份：

```bash
sudo install -d -m 0750 /data/orangejd/backups/config
sudo cp -a /etc/orangejd/orangejd.env /data/orangejd/backups/config/orangejd.env.before-edit
sudo chmod 600 /data/orangejd/backups/config/orangejd.env.before-edit
sudoedit /etc/orangejd/orangejd.env
```

同一天多次编辑时，不得覆盖前一份备份，应改用带时间的明确文件名。

编辑完成后：

```bash
sudo chown root:root /etc/orangejd/orangejd.env
sudo chmod 600 /etc/orangejd/orangejd.env
sudo systemctl restart orangejd
sudo systemctl status orangejd --no-pager
curl -fsS http://127.0.0.1:8081/actuator/health
```

### 5.2 必须保持的生产值

```dotenv
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_DB=orangevc
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
SERVER_ADDRESS=127.0.0.1
ALLOWED_ORIGINS=https://orangevf.com
PUBLIC_BASE_URL=https://orangevf.com
VITE_API_BASE_URL=/api
VITE_OFFICIAL_SITE_URL=https://orangevf.com
VITE_REGISTRATION_ENABLED=true
NGINX_SITE_CONFIG=/etc/nginx/sites-enabled/orangejd
NGINX_SSL_CERTIFICATE=/etc/letsencrypt/live/orangevf.com/fullchain.pem
NGINX_SSL_CERTIFICATE_KEY=/etc/letsencrypt/live/orangevf.com/privkey.pem
```

真实密码、Key 和运营主体值不得出现在本手册。生产配置还必须包含：

- 独立的 `JWT_ADMIN_SECRET` 与 `JWT_APP_SECRET`。
- Cloudflare Turnstile 前端站点 Key 和后端 Secret Key。
- 真实联系邮箱、ICP备案号和官网地址。
- 邮件 SMTP 配置。
- OSS 媒体凭据。
- AI Key 池、兜底 Key、Embedding 和动态 Key 加密密钥。
- GitHub Token、飞书 Webhook，以及启用支付时的支付配置。

### 5.3 前端构建值指纹

`VITE_*` 是构建期配置。发布脚本会把公开构建变量生成 SHA-256 指纹；安装时再与服务器环境文件计算的指纹比较。两者不一致会拒绝发布。

因此，改变 Turnstile 站点 Key、运营信息、ICP备案、官网、注册开关或交易 UI 后，必须重新构建前端，不能只重启后端。

## 6. 标准发布流程

### 6.1 发布前条件

- 本地处于预期 V3 提交，工作区干净。
- 生产公开构建变量已通过安全方式加载到当前终端，且与服务器一致。
- 不在同一发布中夹带数据库手工操作。
- 已确认最近数据库加密备份成功。
- 发布人员知道本次变更影响的用户端、管理端、后端和迁移版本。

发布构建脚本会执行：

- 架构文件大小预算检查。
- Maven `clean verify`。
- 两个前端的锁文件安装、生产依赖审计、Lint、类型检查、测试和构建。
- 品牌扫描和前端包体预算检查。
- 用户端与管理端引用资源完整性检查。
- JAR、两个 SPA、Nginx 模板、systemd 示例和 Flyway 迁移打包。
- 生成 Git 提交、构建时间和核心文件 SHA-256 清单。

### 6.2 本地构建

在 Git Bash 中进入仓库，先从受保护的本地配置加载生产公开构建变量，然后执行：

```bash
cd /d/Orangejd
./scripts/build-release.sh
```

不要设置 `SKIP_TESTS=true` 进行正式发布，不要用 `ALLOW_DIRTY_RELEASE=true` 绕过脏工作区门禁。

构建结果：

```text
build/orangejd-release.tar.gz
build/orangejd-release.tar.gz.sha256
build/install-release.sh
```

### 6.3 上传

Windows PowerShell 示例：

```powershell
$ServerHost = '47.101.131.238'
$SshKey = 'C:\Users\l\.ssh\orangevc.pem'
scp -i $SshKey D:\Orangejd\build\orangejd-release.tar.gz "admin@${ServerHost}:/home/admin/orangejd-release.tar.gz"
scp -i $SshKey D:\Orangejd\build\install-release.sh "admin@${ServerHost}:/home/admin/install-release.sh"
```

本地读取 SHA-256：

```powershell
(Get-FileHash D:\Orangejd\build\orangejd-release.tar.gz -Algorithm SHA256).Hash.ToLower()
```

### 6.4 服务器安装

```bash
chmod 700 /home/admin/install-release.sh
/home/admin/install-release.sh /home/admin/orangejd-release.tar.gz '填写本地计算的SHA256'
```

安装脚本会：

1. 校验压缩包哈希和内部结构。
2. 校验用户端、管理端及引用资源完整性。
3. 校验公开构建配置指纹。
4. 从生产域名和证书路径渲染 Nginx 候选配置。
5. 备份当前 JAR、完整 `web-dist`、环境文件和 Nginx 站点配置。
6. 执行 `nginx -t`。
7. 分阶段切换后端和完整前端目录。
8. 等待应用健康，重新加载 Nginx。
9. 验证用户端、管理端、安全文件、静态资源 404 和安全响应头。
10. 任一步失败时恢复 JAR、前端和 Nginx 文件。

成功输出中的 `Backup:` 路径必须记录到发布单。

### 6.5 发布后业务验收

自动检查通过后仍需人工检查：

1. 未登录访问首页和市场。
2. 用户注册、登录、退出和 Turnstile。
3. 管理端登录、用户分页、作品审核。
4. 作品发布、编辑、重新上传和公开页访问。
5. AI 趋势分析、额度确认、记录保存和详情展示。
6. 橙子画像工坊保存、分享码、导入、主页展示。
7. GitHub 榜单、新手榜单、职业榜单和开源 Issue 页面。
8. 邮箱验证码发送和重新发送时序。

观察日志至少 15 分钟；涉及数据库、额度或任务调度的版本应观察 60 分钟。

## 7. 发布回滚

### 7.1 安装过程自动回滚

安装脚本在应用未健康、Nginx 校验失败或安全验收失败时，会恢复上一 JAR、完整前端目录和 Nginx 配置。数据库迁移不会被自动逆向。

### 7.2 人工文件回滚

仅使用本次安装输出的明确备份目录，先核对内容：

```bash
sudo find /data/orangejd/backups/release-before-YYYYMMDD-HHMMSS -maxdepth 2 -type f -printf '%p\n'
```

确认目标无误后，在维护窗口恢复对应 JAR、完整 `web-dist` 和 Nginx 配置。不得只恢复用户端或只恢复管理端，否则哈希资源可能不匹配。

### 7.3 含 Flyway 迁移的版本

- 向前兼容迁移优先通过旧应用继续读取新结构完成文件回滚。
- 禁止修改 `flyway_schema_history` 假装回滚。
- 禁止删除表或列，除非已有独立备份、恢复演练和明确维护窗口。
- 需要数据逆向时必须制定专项方案，不能套用普通发版回滚。

## 8. Nginx、域名和 HTTPS

### 8.1 当前规则

- `http://orangevf.com`、HTTP www 和 HTTPS www 均重定向到 `https://orangevf.com`。
- API 单 IP 限速 `20r/s`，突发 40。
- 用户端和管理端登录限速 `5r/m`，突发 5。
- API 连接超时 5 秒，读写超时 300 秒。
- WebSocket 读超时 86400 秒。
- 最大请求体 205 MB。
- 隐藏文件、仓库元数据和不存在的静态资源返回 404。
- `/health` 只允许本机访问，Actuator 端口不对公网开放。

### 8.2 修改配置

日常发布应由安装脚本自动渲染和安装 Nginx。必须手工修改时：

```bash
sudo cp -a /etc/nginx/sites-enabled/orangejd /data/orangejd/backups/config/nginx-site.before-edit
sudoedit /etc/nginx/sites-enabled/orangejd
sudo nginx -t
sudo systemctl reload nginx
```

`nginx -t` 失败时不得 reload，应立即恢复备份。

### 8.3 证书检查

```bash
sudo certbot certificates
sudo certbot renew --dry-run
systemctl list-timers --all | grep certbot
```

证书续期后只需 reload Nginx，不需要重启后端。

## 9. 本地 MySQL 8.0

### 9.1 安全基线

- 仅监听 `127.0.0.1:3306`，公网安全组不得开放 3306。
- `require_secure_transport=ON`，应用 JDBC 使用 `sslMode=REQUIRED`。
- 数据库为 `orangevc`，应用账号与备份账号分离。
- 字符集 `utf8mb3`，排序规则 `utf8mb3_general_ci`，时区 `+08:00`。
- `innodb_buffer_pool_size=1536M`，redo 512 MB，最大连接 150。
- 慢查询阈值 1 秒，binlog 保留 3 天。
- 服务器保留 2 GB Swap，仅用于降低突发 OOM 风险。

验证：

```bash
sudo ss -lntp | grep 3306
sudo mysql -N -e "SELECT @@version, @@require_secure_transport, @@max_connections, @@character_set_server, @@collation_server"
sudo mysql -N orangevc -e "SELECT MAX(CAST(version AS UNSIGNED)), SUM(success=0) FROM flyway_schema_history"
```

当前预期 Flyway 最大版本为 37，失败迁移数为 0。表数量核对时要说明是否包含 `flyway_schema_history`，避免口径混淆。

### 9.2 禁止重复迁移切换

`scripts/database/cutover-to-local-mysql.sh` 只用于从 RDS 首次切换到本地 MySQL。当前 `MYSQL_HOST=127.0.0.1` 后不得再次执行。该脚本包含停站、导出、重建数据库和替换环境变量等高风险动作，不属于日常运维命令。

### 9.3 慢查询与连接

```bash
sudo mysql -e 'SHOW GLOBAL STATUS LIKE "Threads_connected"; SHOW GLOBAL STATUS LIKE "Max_used_connections";'
sudo tail -n 100 /var/log/mysql/mysql-slow.log
sudo du -sh /var/lib/mysql
```

不要在高峰期直接终止未知连接；先识别用户、来源、SQL 和事务状态。

## 10. 数据库备份与 OSS 保留

### 10.1 备份流程

每天的备份任务执行：

```text
一致性 mysqldump
  -> gzip -9
  -> age 公钥加密
  -> SHA-256
  -> 上传 database-backups/daily/
  -> 上传 database-backups/checksums/
  -> 回下载并逐字节比较
```

每月 1 日同时生成月备份。服务器本地保留最近 7 天加密文件。

OSS 保留策略：

| 前缀 | 保留时间 |
| --- | --- |
| `database-backups/daily/` | 30 天 |
| `database-backups/checksums/` | 30 天 |
| `database-backups/monthly/` | 400 天 |
| `database-backups/rehearsal/` | 7 天 |

清理规则只允许作用于 `database-backups/`，不得影响 `avatar/`、`cover/`、`detail/`、`general/` 和 `video/`。

### 10.2 手工触发与检查

```bash
sudo systemctl start orangevc-mysql-backup.service
sudo systemctl status orangevc-mysql-backup.service --no-pager
sudo journalctl -u orangevc-mysql-backup --since '2 hours ago' --no-pager -l
sudo /usr/local/sbin/orangevc-verify-latest-production-backup
```

先预演 OSS 清理：

```bash
sudo /usr/local/sbin/orangevc-oss-backup-retention --dry-run
```

确认输出全部位于预期四个前缀后，才允许手工启动正式保留任务。

### 10.3 权限隔离

- 应用媒体 RAM 账号只能访问媒体前缀，必须拒绝 `database-backups/*`。
- 备份 RAM 账号只能访问 `database-backups/*`，必须拒绝用户媒体。
- `/etc/orangejd/mysql-backup.env` 必须为 `root:root 600`。
- 服务器只保存 age 公钥；解密私钥离线保存两份。

### 10.4 恢复演练

至少每月执行一次下载、解密和恢复演练，恢复到独立测试库，不能覆盖 `orangevc`。

仓库的 `restore-encrypted-rehearsal.sh` 会在退出时粉碎传入的私钥文件。因此只能向服务器上传**离线私钥的临时副本**，绝不能传入唯一原件或直接挂载原始私钥。

恢复验收包括：压缩包完整、逐表行数一致、Flyway 无失败、关键用户/作品/额度/AI 记录存在。演练结束后删除临时测试库和临时私钥副本。

## 11. Redis 与知识库

### 11.1 检查

```bash
sudo systemctl status redis-server --no-pager
sudo bash -c 'source /etc/orangejd/orangejd.env; REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli PING'
sudo bash -c 'source /etc/orangejd/orangejd.env; REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli INFO memory | grep -E "used_memory_human|maxmemory_human|maxmemory_policy"'
```

Redis 应只监听本机，启用 AOF，内存策略为 `noeviction`。不得把 `FLUSHALL`、`FLUSHDB` 当作普通故障处理。

### 11.2 向量知识库

通用知识、新手榜单、职业榜单和项目索引状态由应用与数据库共同维护。发布不应清空 Redis。若索引异常，应先检查：

1. Redis 与 Search 命令是否可用。
2. Embedding Key、Endpoint 和模型是否正确。
3. 数据库中的知识文档和项目索引状态。
4. 应用日志中的解析、限流或向量维度错误。

重建索引属于可能消耗模型额度和服务器资源的操作，必须在低峰期执行并记录重建范围。

## 12. AI 工具与外部任务

### 12.1 AI Key 池

当前生产设计支持：

- `GITEE_AI_KEY_1` 至 `GITEE_AI_KEY_10` 的主 Key 池。
- `AI_TREND_*` 等供应商配置作为相应业务或兜底来源。
- `AI_TOOL_POOL_ENABLED=true` 时统一调度。
- 全局并发上限通过 `AI_TOOL_GLOBAL_MAX_CONCURRENCY` 配置，当前目标值为 80。
- `AI_CONFIG_ENCRYPTION_KEY` 用于管理端动态 API Key 加密保存。

修改 Key 后只重启后端即可；修改前端开关或公开构建值则必须重新发布。日志和管理端截图不得显示完整 Key。

### 12.2 自动重试与记录

AI 请求失败时由运行时负责重试、Key 租约和结果记录。发现大量失败时不要让用户反复点击，应检查：

- Key 池占用和供应商 429/5xx。
- 请求是否超过租约或 Nginx 300 秒读超时。
- AI 记录是否进入终态、额度流水是否幂等。
- 供应商模型名、Endpoint 和响应 JSON 格式。

真实 Key 压测不进入 CI；正式压测应设置独立窗口、并发上限和费用预算。

### 12.3 GitHub 榜单与开源 Issue

每周榜单、新手榜单、职业榜单和开源 Issue 的调度配置不同。抓取异常时按顺序检查：

1. `GITHUB_TOKEN` 是否有效且未触发限流。
2. 应用日志中的 GitHub 状态码和 JSON 解析错误。
3. 数据库最新快照时间与任务运行记录。
4. 翻译/AI 阶段是否失败，避免把“抓取成功、翻译失败”误判为完全抓取失败。
5. 对应项目是否进入知识库索引状态。

不要因某个榜单成功就推断所有榜单共用同一抓取链路。

### 12.4 支付与智能设备

- 订单支付只有在 `EPAY_ORDER_PAYMENTS_ENABLED=true` 且商户、网关、签名密钥、通知地址和返回地址全部验收后才能开放。
- Nginx 对 `/api/epay/notify` 有专门代理规则，用于保留回调路径；修改通用 `/api/` 代理时必须单独回归支付通知验签和幂等入账。
- 支付故障不得通过手工修改订单和额度流水快速补偿，应先依据支付平台订单号、平台订单号和幂等记录核账。
- StackChan/Agent 设备依赖 WebSocket、设备绑定和动作任务。设备离线先检查 `/ws/` 连接、反向代理 Upgrade 头、设备 Token 和任务状态，不要直接删除设备记录。

## 13. 注册、Turnstile 与邮件

### 13.1 注册链路

生产注册应保持 `VITE_REGISTRATION_ENABLED=true`。完整链路为：

```text
前端 Turnstile 站点 Key
  -> orangevf.com 在 Cloudflare 允许主机名中
  -> 后端 TURNSTILE_SECRET_KEY 校验
  -> 注册或找回密码业务
```

“无法连接到网站”优先检查站点 Key 与 Secret 是否属于同一 Turnstile Widget、主机名是否包含 `orangevf.com`、前端是否用最新 Key 重新构建。

### 13.2 邮件验证码

```bash
sudo journalctl -u orangejd --since '30 minutes ago' --no-pager -l | grep -Ei 'mail|smtp|verification|验证码|timeout|auth'
```

检查 SMTP 主机、端口、授权码、STARTTLS/SSL 组合和供应商退信。验证码重新发送需同时遵守前端倒计时、后端冷却和验证码有效期；邮箱尚未注册不应影响“找回密码”以外场景的错误语义。

平台无法保证覆盖所有邮箱服务商；教育邮箱可能有灰名单、延迟或反垃圾策略，应提供明确错误提示并避免泄露账号是否存在。

## 14. OSS 媒体

- Bucket 保持私有，禁止公共读和匿名列举。
- 用户媒体通过短时签名 URL 访问，当前默认有效期 300 秒。
- 应用媒体账号不得访问数据库备份前缀。
- 不要改变已有媒体对象 Key 或数据库地址。
- 上传异常先检查 OSS Endpoint、地域、RAM 权限、对象大小和应用日志。
- 用户外链只允许安全 HTTPS 公网地址；后端不主动抓取用户链接，避免 SSRF。

## 15. 公开内容与 Google 安全复审

发布前或复审前运行只读审计脚本。脚本扫描已审核且公开的作品与需求，不请求用户外链，也不修改数据库。发布包当前不携带运维脚本；执行前应把仓库中同一提交的 `scripts/audit_public_content.py` 作为独立只读工具上传到服务器受限目录，并校验 SHA-256，不能使用来源不明的旧副本。

```bash
sudo bash -c '
set -a
source /etc/orangejd/orangejd.env
set +a
cd /home/admin
python3 audit_public_content.py --fail-on-high \
  --json-output /data/orangejd/backups/public-content-audit.json \
  --csv-output /data/orangejd/backups/public-content-audit.csv
'
```

报告中的高风险项必须由管理员人工取消公开或重新审核。提交 Google 复审前还要确认：

- 规范域名、HTTP 和 www 跳转正确。
- sitemap 只列出希望收录的公开页面，登录页为 `noindex` 且不在 sitemap。
- 隐藏路径和不存在资源返回 404。
- 公开内容不存在仿冒登录、诱导下载、异常跳转或收集凭据。
- 真实运营信息、联系邮箱和ICP备案号可见且一致。

Search Console 中“网页会自动重定向”的 `http://orangevf.com/` 是规范 HTTPS 跳转时属于预期，不需要取消 HTTPS 重定向。

## 16. 健康检查与告警

数据库健康脚本每 15 分钟检查：

- MySQL、后端、Nginx 和备份定时器是否 active。
- 本地 MySQL 是否可查询。
- Actuator 健康端点，最多 3 次、每次 10 秒、间隔 2 秒。
- 应用是否仍配置 `MYSQL_HOST=127.0.0.1`。
- 根磁盘使用率。
- 最近本地加密备份是否早于 26 小时。

磁盘达到 70% 写入 warning，达到 85% 视为失败并发送飞书告警。

收到 `application health endpoint failed` 时：

```bash
curl -v --max-time 10 http://127.0.0.1:8081/actuator/health
systemctl status orangejd --no-pager
sudo journalctl -u orangejd --since '20 minutes ago' --no-pager -l
sudo journalctl -u orangevc-database-healthcheck --since '20 minutes ago' --no-pager -l
free -h
df -h /
```

若随后自动恢复且应用日志无崩溃，可能是短时 GC、数据库等待或旧版探针超时；仍应核对服务器已安装当前带三次重试的健康脚本。

## 17. 常见故障处理

| 现象 | 首查 | 处理边界 |
| --- | --- | --- |
| 全站 502 | `orangejd` 状态、8080 监听、后端日志 | 修复根因后再重启 |
| `/admin` 500 | Nginx error、`web-dist/admin/index.html`、管理端资源 404 | 必须恢复完整前端包，不能只拷贝 HTML |
| 页面样式全崩 | HTML 引用的哈希资源是否存在、缓存、是否漏发管理端 | 使用统一发布包重新安装 |
| 数据库连接失败 | MySQL 状态、3306 本地监听、TLS、账号、磁盘 | 不得临时开放公网 3306 |
| 飞书数据库告警 | 健康脚本日志和实际 Actuator | 区分短时探针失败与服务宕机 |
| GitHub 快照不更新 | Token、限流、JSON 解析、任务日志、快照时间 | 不要直接删除旧快照 |
| 新手榜成功但周榜失败 | 分别检查各自抓取与翻译链路 | 两者机制不同，不能类推 |
| Turnstile 无法连接 | Widget 主机名、前后端 Key 配对、前端构建指纹 | 换站点 Key 后重新发布前端 |
| 邮箱收不到验证码 | SMTP 日志、授权码、TLS、垃圾箱、教育邮箱策略 | 不无限重发，遵守冷却 |
| AI 长时间无结果 | Key 池、429/5xx、租约、模型名、记录终态 | 保证额度和记录幂等 |
| 磁盘告警 | MySQL、日志、本地备份、发布备份占用 | 先识别大文件，禁止盲目递归删除 |

## 18. 重启与维护窗口

### 18.1 可直接执行的低风险操作

```bash
sudo nginx -t && sudo systemctl reload nginx
sudo systemctl restart orangejd
sudo systemctl start orangevc-mysql-backup.service
```

每次重启后都要检查 Actuator、用户端和管理端。

### 18.2 必须安排维护窗口

- MySQL 重启、配置变更、升级或数据恢复。
- Redis 清理或索引全量重建。
- 数据库账号、字符集、排序规则和 TLS 变更。
- RDS/本地 MySQL 切换。
- 大批量数据修复或额度流水修复。
- 可能超过 5 分钟的 Nginx/证书结构调整。

### 18.3 明确禁止

- 在生产执行未经核对的递归删除。
- 用 `git reset --hard`、`git clean` 或服务器 `git pull` 代替发布。
- 手工删除 Flyway 历史或修改已执行迁移。
- 在日志、命令行参数或工单中暴露密码和 Key。
- 同时重启 MySQL、Redis、Nginx 和后端后再猜测根因。
- 将数据库备份解密私钥长期留在服务器。

## 19. 灾难恢复

### 19.1 恢复优先级

1. 确认事件范围并停止继续写入。
2. 保存现场日志、服务状态和磁盘信息。
3. 选择经过校验的最近加密备份。
4. 在独立数据库完成解密恢复演练。
5. 核对 Flyway、逐表行数和关键业务记录。
6. 在维护窗口恢复生产库。
7. 启动后端，完成只读验证和关键写入验证。
8. 恢复公网并持续观察。

恢复目标是最多丢失 24 小时数据，但实际恢复点由最近成功且可解密的备份决定。

### 19.2 旧 RDS 回滚限制

只有在本地数据库切换后、尚未恢复公开写入前，才可直接恢复旧环境变量连接 RDS。公开写入后若必须回 RDS，应先停站，把本地 MySQL 最新数据完整回灌并核对新增用户、投稿、额度和 AI 记录。

## 21. 代码与生产不一致时的处理

1. 先记录本地提交、远端 V3 提交和生产 JAR/前端清单哈希。
2. 只读比较，不在服务器直接改源码。
3. 服务器临时修复必须回补到本地 V3，并经过完整测试重新发布。
4. 数据库运维脚本更新后，要明确安装到 `/usr/local/sbin` 和 systemd 的对应版本；代码仓库更新不等于服务器脚本已更新。
5. 发布后把 Git 提交、发布包 SHA、服务器备份目录、Flyway 版本和验收结果写入发布记录。
