# 本地项目上线流程提示词手册

> 用途：把一个只在开发者电脑运行的项目，交给没有历史记忆的 AI，分阶段完成代码审计、部署选型、生产改造、服务器部署、上线验收和持续运维。
>
> 本手册来自 OrangeJD 的实际上线过程，但提示词设计为可复用于 Java、Node.js、Python、Go、PHP、前后端分离、单体和轻量微服务项目。

## 1. 使用方法

不要一次把所有阶段都交给 AI。推荐每次只执行一个阶段，并把上一阶段生成的文档作为下一阶段输入。

开始前准备以下信息；未知项可以写“未知”，让 AI 从代码或当前环境中查找：

```text
项目目录：<绝对路径>
目标用户：<内部使用/邀请测试/公众用户/企业客户>
预计首月用户：<数量或未知>
预计同时在线：<数量或未知>
预计上传类型：<图片/视频/文档/无>
预计数据增长：<每月大致容量或未知>
预算：<月预算和首年预算>
目标地域：<中国内地/中国香港/海外/未知>
是否需要交易支付：<是/否/后续>
是否已有域名和备案：<状态>
云厂商偏好：<阿里云/腾讯云/AWS/无>
可接受停机时间：<例如每月 1 小时>
可接受数据丢失：<例如最多 24 小时>
```

建议在项目中建立以下交付目录：

```text
docs/上线/
├── 01-代码与部署形态评估.md
├── 02-生产资源选型与容量规划.md
├── 03-生产就绪改造清单.md
├── 04-部署实施手册.md
├── 05-上线前安全与合规清单.md
├── 06-生产验收报告.md
├── 07-运维与故障处理手册.md
└── 08-生产现状与交接记录.md
```

## 2. 所有阶段共用的总控提示词

每次执行阶段提示词前，先附上下面这段总控约束。

```text
你是一名负责把本地项目安全上线的资深架构师、开发工程师、测试工程师和运维工程师。请直接读取项目代码和现有文档，不要只根据 README 或我的描述推断。

工作规则：
1. 先检查项目结构、Git 状态、构建文件、配置文件、数据库迁移、前后端请求地址、文件存储、缓存、定时任务、外部 API、鉴权和部署脚本，再给结论。
2. 每个关键结论必须给出代码文件、配置项或命令输出作为依据；明确区分“代码已确认”“服务器已确认”“用户口述”“尚未验证”。
3. 不得复述、写入或提交任何真实密码、Token、AccessKey、私钥、Webhook 和数据库连接密钥。只报告变量名和 OK/MISSING。发现秘密进入 Git 或日志时，提出轮换方案。
4. 不覆盖我已有的未提交改动，不擅自删除数据，不执行不可逆数据库操作。所有发布、迁移和清理必须先备份并给出回滚步骤。
5. 命令必须标明运行位置：本地 Windows PowerShell、本地 macOS/Linux、服务器终端或云控制台。不要混用命令语法。
6. 涉及价格、云产品试用、备案、证书、政策、产品规格或软件当前版本时，查询官方最新资料并附链接；不要依赖过时记忆。
7. 容量评估不能只写“支持多少用户”，必须分别估算注册用户、日活、同时在线、平均/峰值请求、数据库连接、带宽、对象存储、缓存和后台任务，并给出假设。
8. 优先沿用项目现有技术栈和部署方式。除非有明确收益，不要为了“高级”而引入 Kubernetes、复杂微服务或昂贵托管产品。
9. 若任务要求实施修改，应完成代码修改、测试、构建、发布物哈希和文档更新；若只能给方案，明确哪些步骤尚未执行。
10. 每个阶段最后输出：已确认事实、风险清单、建议方案、待办清单、验收门槛、下一阶段所需输入。

只有真正阻塞且无法从代码和环境查到的信息才向我提问；其他情况采用保守假设继续，并清楚标注假设。
```

## 3. 阶段一：判断部署形态

### 3.1 目标

判断项目适合继续本地运行、部署到单台服务器、使用云托管平台，还是拆分数据库、对象存储和缓存。这里的“本地部署”应区分开发环境、企业内网部署和把个人电脑当公网服务器三种情况。

### 3.2 提示词

```text
项目目录是：<项目绝对路径>。

请执行“部署形态评估”，直接读取代码后回答：
1. 识别技术栈、进程数量、前端形态、端口、数据库、缓存、搜索/向量能力、文件上传、定时任务、WebSocket、消息队列、AI 服务和所有外部 API。
2. 找出项目在本地运行时依赖的隐含资源，例如本地磁盘路径、localhost、Windows 路径、开发数据库、Docker 容器、内存缓存、硬编码 IP、开发代理和测试账号。
3. 判断以下方案是否可行并分别说明原因、优点、缺点、风险和适用阶段：
   - 开发者电脑本地运行
   - 企业内网本地部署
   - 单台公网服务器全量部署
   - 应用服务器 + 托管数据库 + 对象存储
   - 容器平台或 PaaS
   - 完整云原生/多节点部署
4. 从数据安全、稳定性、公网带宽、断电断网、备份、扩容、域名 HTTPS、合规和运维成本角度比较本地与服务器部署。
5. 给出当前阶段的唯一推荐方案，同时给出一个低预算备选方案和未来扩容路径。
6. 列出阻碍部署的代码问题，并按 P0/P1/P2 排序。

输出到 docs/上线/01-代码与部署形态评估.md，并在回复中给出不超过 15 行的结论摘要。未经我确认，本阶段不要购买云资源，也不要修改生产服务器。
```

### 3.3 验收门槛

- 已找到所有运行进程和监听端口。
- 已找到所有持久化数据位置。
- 已找到所有外部依赖和环境变量。
- 已说明为什么个人电脑不适合或适合长期公开服务。
- 推荐方案包含故障边界和扩容路径，不只是产品名称。

## 4. 阶段二：生产资源选型与容量规划

### 4.1 目标

根据代码实际行为和预算，选择服务器、数据库、对象存储、Redis/搜索、邮件、域名、证书、监控、备份和可选 CDN，而不是机械套用固定配置。

### 4.2 提示词

```text
请基于项目代码和 docs/上线/01-代码与部署形态评估.md，完成生产资源选型。

我的约束：
- 预算：<填写>
- 地域：<填写>
- 首月用户/日活/同时在线：<填写或未知>
- 上传类型和增长：<填写或未知>
- 可接受停机和数据丢失：<填写>

要求：
1. 从代码推导 CPU、JVM/运行时内存、数据库连接、Redis 内存、磁盘、对象存储、出网带宽和后台任务负载。无法精确计算时给出保守假设和公式。
2. 至少比较三档方案：极低预算试运营、推荐生产起步、用户增长后的升级方案。
3. 对每档列出：应用服务器 vCPU/内存/系统盘/带宽、数据库版本/规格/存储/高可用、Redis 类型和内存、对象存储类型/容量/下行流量、备份、监控、域名证书和月成本区间。
4. 检查项目是否需要 Redis 模块、RediSearch、向量索引、持久化或特殊版本。不能用普通云 Redis 替换项目需要的模块，除非已经验证兼容。
5. 判断文件应该保存在服务器磁盘还是对象存储；说明私有 Bucket、签名 URL、跨域、生命周期、同城冗余/本地冗余和下行流量成本。
6. 数据库选择必须说明单机、基础版、高可用版、读写性能、连接数、备份、迁移和到期后的搬迁方式。不要因“分析版”名称高级就选择不匹配业务的产品。
7. 说明固定带宽和按流量计费的差异，估算图片/视频对带宽和 OSS 下行流量的影响。
8. 查询目标云厂商当前官方价格、试用期限、续费价格和限制。试用不等于长期成本，必须给出到期迁移预案。
9. 给出容量边界表：在什么同时在线、峰值 RPS、数据库容量、Redis 内存、OSS 流量和磁盘使用率下需要升级。
10. 输出一张最终采购清单，标明“立即购买”“免费试用”“按量开通”“暂不需要”。

输出到 docs/上线/02-生产资源选型与容量规划.md。不要替我下单。
```

### 4.3 要求 AI 使用的容量表达方式

```text
不要回答：“4 核 8G 可以支持 1 万用户。”

应回答：
- 注册用户：不直接决定服务器容量。
- 日活用户：用于估算每天请求和存储增长。
- 同时在线：决定连接数和瞬时内存。
- 峰值 RPS：决定应用 CPU、线程池和数据库压力。
- 文件下行：决定公网带宽和 OSS 费用。
- AI/向量请求：通常是延迟和外部配额瓶颈。
- 后台任务：应与前台请求错峰，并设置超时、重试和降级。
```

## 5. 阶段三：生产就绪代码审计与改造

### 5.1 目标

在上服务器前，把“只能在开发机运行”的代码改造成可配置、可迁移、可观测、可回滚的生产版本。

### 5.2 提示词

```text
请对项目执行生产就绪审计，并在不破坏现有行为的前提下实施必要的 P0 修改。

检查范围：
1. 环境变量：数据库、Redis、JWT、邮件、对象存储、AI、验证码、Webhook、支付和跨域配置是否可由生产环境注入。
2. 开发残留：localhost、127.0.0.1、Windows 绝对路径、开发代理、测试密钥、演示账号、调试接口和 Swagger。
3. 数据库：建表脚本与 ORM/Mapper 字段是否一致；是否使用 Flyway/Liquibase；迁移是否向后兼容；首次部署和已有数据升级是否安全。
4. 文件：上传校验、文件头校验、大小限制、对象归属、目录限制、私有读取、替换和删除旧对象是否完整。
5. 缓存与搜索：Redis 密码、绑定地址、持久化、最大内存、淘汰策略、索引初始化和重建能力。
6. 定时任务：cron、时区、重复执行、漏跑补偿、并发锁、外部请求超时、重试、幂等、旧数据回退和日志。
7. 安全：认证、越权、IDOR、CORS、SSRF、文件上传、管理接口、健康详情、支付回调和日志脱敏。
8. 前端：生产 API 基址、WebSocket、静态路由回退、资源路径、Turnstile Site Key、缓存更新和构建产物。
9. 可观测性：健康接口、请求 ID、错误日志、关键任务日志和日志轮转。
10. 发布：提供生产配置示例、systemd/Docker Compose、Nginx 模板、构建脚本、发布物哈希和回滚方式。

实施要求：
- 先列出将修改的文件和原因，再开始修改。
- 为高风险逻辑添加测试。
- 运行后端测试、前端构建和配置扫描。
- 不把真实秘密写入项目。
- 输出修改摘要、测试结果、未解决风险和发布物 SHA256。
- 更新 docs/上线/03-生产就绪改造清单.md。
```

### 5.3 重点经验

- `.gitignore` 写了 `target/` 不代表历史编译产物已从 Git 索引移除，应检查跟踪状态。
- 数据迁移前必须检查代码字段与 Flyway 是否一致，不能靠生产环境手工补列代替迁移文件。
- “Redis 可连接”不代表 RediSearch/向量能力可用，应实际调用模块命令和检索接口。
- 定时任务的写入频率必须与读取回退窗口一致。周更快照不能只读取今天和昨天。
- 外部 API 需要超时、限流处理、幂等、可观测日志和旧数据降级。
- 私有 OSS 不能把永久公开 URL 当作权限模型，应通过受控媒体接口或短期签名 URL 读取。

## 6. 阶段四：部署方案和云资源实施

### 6.1 提示词

```text
请基于前面三份文档，生成并协助执行首次生产部署手册。

要求按顺序覆盖：
1. 云资源地域、VPC/内网互通和资源命名。
2. 服务器操作系统和基础软件安装。
3. 数据库实例、数据库、最小权限账号、SSL 和白名单。
4. Redis 安装方式、模块能力、密码、仅本机监听、AOF、内存上限和开机启动。
5. 私有对象存储 Bucket、专用 RAM/IAM 用户、仅目标 Bucket/目录权限、跨域和服务端加密。
6. 生产环境变量文件、所有者和权限。
7. 后端 systemd 或容器服务，资源限制和自动重启。
8. 前端静态文件和 Nginx 反向代理。
9. 数据库迁移、本地数据导入、上传文件迁移和向量索引重建。
10. 域名、DNS、备案、HTTPS、CORS、WebSocket 和验证码域名。
11. 防火墙、管理入口和健康接口限制。
12. 备份、回滚和部署后验证。

命令输出规则：
- 每段命令前写清楚运行位置。
- 使用占位符，不在命令中回显真实密码。
- 长脚本使用 set -euo pipefail，并在危险操作前检查目标路径和备份。
- 上传、解压、安装、重启和验证分开，不把所有操作塞进一条难以排错的命令。
- 给出预期输出和失败时的停止条件。

把最终内容写入 docs/上线/04-部署实施手册.md。每完成一步就在文档状态表中标记：未开始/执行中/已验证/失败。
```

## 7. 阶段五：真正开放前的工作

### 7.1 提示词

```text
项目已部署到服务器，但尚未正式公开。请执行上线前门禁审计，不要因为健康接口返回 200 就判定可以上线。

检查并协助完成：
1. 版本一致性：Git 提交、发布物哈希、服务器文件哈希、数据库迁移版本和前端构建版本可追溯。
2. 网络入口：普通公网只开放 80/443；SSH 限定来源并使用密钥；数据库、Redis、应用端口不对公网开放。
3. 数据库白名单和最小权限；Redis 仅本机监听；环境文件权限 600。
4. 修改默认管理员密码，禁用演示/测试账号，检查跨账号越权。
5. 禁用 Swagger/OpenAPI；限制健康详情、管理静态页面和管理 API。
6. 正式域名、备案、HTTPS、HTTP 跳转、CORS、WebSocket、Turnstile/验证码域名。
7. 用户协议、隐私政策、账号注销、数据删除、内容规范、侵权投诉和适用的备案展示。
8. 支付功能必须经过签名、金额、重复回调、退款和对账验证；未完成时隐藏或禁用交易入口。
9. RDS、Redis、OSS 和应用备份；至少做一次恢复演练。
10. CPU、内存、磁盘、5xx、服务存活、数据库容量、OSS 流量、余额和到期告警。
11. 外部服务配额：邮件、短信、AI、GitHub、OSS、支付和 Webhook。
12. 降级方案：AI、GitHub、邮件、OSS 或 Redis 临时不可用时，核心页面是否仍可使用。

输出 docs/上线/05-上线前安全与合规清单.md。使用表格记录每项证据和状态。任何 P0 未完成时明确写“禁止公开上线”，不要用模糊措辞。
```

## 8. 阶段六：测试和验证能否成功上线

### 8.1 提示词

```text
请为当前项目设计并执行生产验收。测试必须通过正式入口访问，不得只测 localhost 后端接口。

测试分层：
1. 基础设施：DNS、HTTPS、证书链、Nginx、systemd/容器、数据库、Redis、对象存储和磁盘。
2. 健康与迁移：应用健康、Flyway/Liquibase、数据库核心表数量、缓存/搜索索引、定时任务。
3. 身份链路：发送验证码、注册、登录、刷新/过期 Token、退出、找回密码、管理员登录。
4. 核心业务：按实际代码列出完整用户旅程，不遗漏草稿、审核、修改、删除、状态流转和异常分支。
5. 媒体文件：图片、视频、文档的上传、私有读取、替换、删除、对象归属和数据库地址。
6. AI/RAG：真实向量检索、真实 AI 请求、无知识命中、外部 API 超时和余额不足。
7. 多账号权限：用户 A 不能读取或修改用户 B 的草稿、订单、会话、媒体和个人数据。
8. 管理能力：审核、封禁、配置、审计日志和受限公网访问。
9. 浏览器与设备：桌面 Chrome/Edge、Android、iPhone；检查响应式、缓存和上传。
10. 性能：基础并发、慢接口、数据库连接池、JVM/进程内存、带宽和大文件。
11. 故障演练：重启应用、短时断开 Redis/外部 AI、恢复数据库备份、回滚上一版本。
12. 安全复测：端口扫描、Swagger、健康详情、CORS、上传绕过、越权和日志秘密。

每个用例记录：编号、前置条件、操作、预期、实际、证据、结果、严重级别和修复版本。

最终输出 docs/上线/06-生产验收报告.md，并给出唯一结论：
- GO：可以公开上线
- CONDITIONAL GO：只允许小范围测试，并列出限制
- NO-GO：禁止上线，并列出 P0 阻断项
```

### 8.2 最低业务验收矩阵

| 范围 | 最少验证 |
| --- | --- |
| 访客 | 首页、列表、详情、搜索、错误页 |
| 新用户 | 验证码、注册、登录、找回密码 |
| 普通用户 A | 编辑资料、上传头像、创建草稿、提交审核 |
| 普通用户 B | 无法访问 A 的私有数据，公开内容显示作者资料正确 |
| 管理员 | 登录、审核、驳回、封禁、审计 |
| 文件 | 上传、读取、替换、删除、非法类型、超限文件 |
| 数据 | 数据库迁移、核心表数量、备份恢复 |
| AI/搜索 | 向量数量、真实检索、真实生成、失败降级 |
| 运维 | 重启、日志、告警、回滚、定时任务 |

## 9. 阶段七：正式开放和发布窗口

### 9.1 提示词

```text
生产验收结论已经是 GO。请生成正式开放执行单，并陪同逐项执行。

要求：
1. 确定发布时间、负责人、观察窗口和停止变更时间。
2. 发布前再次备份数据库、应用包、前端文件、Nginx 配置和 Redis 数据。
3. 记录 Git 提交、Tag、发布物哈希、迁移版本和云资源状态。
4. 按“上传到临时目录 -> 校验哈希 -> 备份旧版 -> 安装 -> 重启 -> 健康检查 -> 业务冒烟”发布。
5. 数据库迁移失败、健康检查失败、错误率异常或核心链路失败时立即停止并回滚。
6. 放开域名流量后持续观察日志、5xx、CPU、内存、数据库连接、Redis、OSS、邮件和 AI 配额。
7. 形成上线时间线、异常记录和最终结果。

不要在没有备份、回滚包或验收报告的情况下执行正式开放。
```

## 10. 阶段八：上线后运维

### 10.1 提示词

```text
项目已经正式上线。请基于代码、云资源和生产配置生成长期运维手册。

至少包含：
1. 每日、每周、每月巡检项目及命令。
2. 应用、Nginx、数据库、Redis、对象存储、磁盘和外部 API 的监控指标与阈值。
3. 日志路径、日志轮转、请求 ID、错误检索和敏感信息处理。
4. RPO/RTO、备份周期、异地副本、恢复演练和备份有效性检查。
5. 日常发版、数据库迁移、前端更新、回滚和紧急修复流程。
6. 用户增长后的扩容触发条件和顺序：优化慢查询/缓存 -> 垂直升级 -> 拆分服务或读写压力。
7. OSS 容量、请求、下行流量、生命周期和费用控制。
8. 密钥、证书、域名、服务器、数据库和试用资源的到期日历。
9. 安全更新、依赖漏洞、管理员账号、SSH Key 和密钥轮换周期。
10. 故障分级、响应人、通知渠道、止损、恢复、复盘模板。

输出 docs/上线/07-运维与故障处理手册.md，并生成一个不包含秘密值的 docs/上线/08-生产现状与交接记录.md。
```

## 11. 常用专项提示词

### 11.1 生产故障排查

```text
生产出现以下故障：<现象、时间、用户影响>。

请按“入口 -> Nginx -> 应用进程 -> 应用日志 -> 数据库/Redis/OSS -> 外部 API -> 最近发布”的顺序排查。先收集只读证据，不要重启或改配置掩盖现场。输出最可能原因、证据、临时止损、永久修复、验证方法和是否需要回滚。不得在回复中打印秘密。
```

### 11.2 日常版本发布

```text
请检查当前 Git 工作区和生产现状，识别本次修改涉及后端、用户端、管理端、数据库迁移、配置和静态资源中的哪些部分。运行必要测试，构建最小发布物，计算 SHA256，生成上传、备份、部署、验证和回滚命令。不要覆盖无关未提交改动，也不要把“构建成功”当作“生产已部署”。
```

### 11.3 数据库或 OSS 搬迁

```text
当前需要把 <数据库/OSS> 从 <来源> 迁移到 <目标>。请先读取代码确认数据模型、对象键、数据库中保存的地址形式和访问权限。设计全量导出、增量同步或停机窗口、校验数量与哈希、应用配置切换、回滚和旧资源保留期。涉及删除旧数据时必须等新环境验收和备份确认后再执行。
```

### 11.4 成本与容量复盘

```text
请根据最近 30 天的 CPU、内存、磁盘、数据库容量/连接、Redis 内存、OSS 存储/下行/请求、带宽和账单，判断当前资源是否过配或接近瓶颈。把固定成本、按量成本和即将到期的试用分开，给出本月优化动作和未来三档扩容触发条件。不要只按注册用户数估算。
```

### 11.5 交接给新 AI

```text
你将接手一个已经部署的项目。请先读取：README、架构文档、生产部署手册、Git 状态、最近提交、生产配置示例、数据库迁移、Nginx/systemd/容器文件和最新验收报告。输出“已确认生产现状、尚未确认事项、当前发布版本、云资源、秘密变量名、备份状态、P0 风险和下一步”。不要根据旧对话猜测生产状态，也不要复述秘密值。
```

## 12. AI 输出质量检查表

在采纳 AI 的部署建议前，逐项确认：

- [ ] AI 实际读取了代码，而不是只复述 README。
- [ ] 所有关键结论都有文件或命令证据。
- [ ] 明确区分本地完成、发布物生成、上传完成和生产验收。
- [ ] 资源建议包含负载假设、容量边界和升级条件。
- [ ] 区分数据库、缓存、搜索/向量库和对象存储的职责。
- [ ] 说明试用到期、数据搬迁和长期成本。
- [ ] 所有秘密只使用变量名或占位符。
- [ ] 危险操作前有备份，修改后有验证，失败时有回滚。
- [ ] 命令明确标注运行环境，不混用 PowerShell 和 Bash。
- [ ] 真实测试覆盖域名入口、核心业务和多账号权限。
- [ ] 上线结论是 GO、CONDITIONAL GO 或 NO-GO，而不是模糊的“基本可以”。
- [ ] 生产手册已更新，下一位没有记忆的 AI 可以继续工作。

## 13. 推荐阶段顺序

```text
阶段一：代码与部署形态评估
  -> 阶段二：资源选型与容量规划
  -> 阶段三：生产就绪代码改造
  -> 阶段四：云资源和首次部署
  -> 阶段五：安全、域名、合规、备份与监控
  -> 阶段六：生产验收和 GO/NO-GO
  -> 阶段七：正式开放
  -> 阶段八：长期运维、升级和迁移
```

不要跳过阶段五和阶段六。项目能在公网 IP 打开、后端健康接口返回 200、数据库显示 `UP`，都只能证明部分组件存活，不能单独证明项目已经可以正式上线。
