# RAG A/B 60 题质量与成本基准报告

实验时间：2026-09-29（Asia/Shanghai）

## 修正后结论

B 版在修改排序后严格通过全部 60 题，通过率为 100%；A 版通过 19 题，通过率为 31.7%。带来源金标的 53 题全部在前 8 找到正确来源，来源 Recall@8 从修改前的 81.1% 提升到 100%。硬条件、来源追溯、引用就绪和无依据拒答均保持 100%。

B 版热态 P95 为 384 ms，低于修改前的 417 ms，也满足当前 `P95 ≤ 500 ms` 的实验门槛。这说明本轮排序修正同时达到了当前自动评测的质量与延迟门槛。由于题目来自现有资料且部分问题直接包含项目名，仍需独立人工盲测和持续双跑后才能替换 A 版。

## 测试范围

- 语料：68 份 `READY` 文档、1,307 个有效分块。
- 参数：`topK=8`，相似度阈值 `0.55`。
- 题目：60 题，且不复用此前用于修正实现的 12 题冒烟集。
- 57 题预期回答，3 题预期拒答；53 题标注了期望来源。
- 本轮只评估检索和回答策略，不调用文本生成模型。

题目由当前知识库资料构造并绑定来源金标，可以稳定回归来源召回和业务规则。它还不是独立业务人员制作的盲测集，且部分问题包含项目名，因此结果不能当作生产真实准确率。

## 总体结果

| 指标 | A 版 | B 版 |
|---|---:|---:|
| 严格通过率 | 31.7%（19/60） | **100%（60/60）** |
| 来源 Recall@8 | 37.7%（20/53） | **100%（53/53）** |
| 应回答用例可追溯率 | 未统计 | 100%（57/57） |
| 应回答用例引用就绪率 | 未统计 | 100%（57/57） |
| 拒答准确率 | 未单独统计 | 100%（3/3） |
| P50 | 219 ms | 274 ms |
| P95 | 372 ms | **384 ms** |

B 版 P50 比 A 版增加 55 ms，P95 增加 12 ms。增加的时间来自独立 HNSW/全文混合检索、业务状态复核、硬条件复核和证据组织。当前规模下 P95 仍在门槛内。

## 分题型结果

| 题型 | 数量 | A 版通过 | B 版通过 |
|---|---:|---:|---:|
| 入门项目精确来源 | 15 | 7 | 15 |
| 职业项目精确来源 | 15 | 6 | 15 |
| GitHub README 精确来源 | 15 | 5 | 15 |
| Java 职业项目 | 5 | 0 | 5 |
| Vue 硬条件 | 3 | 0 | 3 |
| 岗位、依赖条件与拒答 | 7 | 1 | 7 |

B 版在全部题型上通过。15 个硬条件与行为题继续全部通过，说明标题排序修改没有破坏语言规范化、业务元数据过滤、资料状态复核和拒答策略。45 个按具体项目或仓库定位的问题也由 35 个提升到 45 个。

| `career-kibana` | `career:260` | 第 1 名命中 |
| `github-freecodecamp` | `freeCodeCamp/freeCodeCamp` | 第 1 名命中 |
| `github-irremote` | `crankyoldgit/IRremoteESP8266` | 第 1 名命中 |
| `github-pixel2motion` | `nolangz/pixel2motion` | 第 1 名命中 |
| `github-canvas-ui` | `DavidHDev/canvas-ui` | 第 1 名命中 |

这些失败都不是空检索、硬条件误杀、下架状态误判或拒答错误。每题都返回 8 条结果，`answerPolicy` 都是 `ANSWER_WITH_CITATIONS`，证据也都可追溯。失败排名中还能看到同一来源的多个分块反复占位，例如 `github-irremote` 的前 8 条里 6 条来自 `HKUDS/nanobot`。

修正后，全文通道使用 OR 词项召回，分别检索正文以及 `title/sourceRef`。混合排序新增名称通道权重，并在规范化后的问题确实包含完整项目名时增加确定性精确名称分。最终截断还会先覆盖不同 `sourceRef`，再用剩余名额补充同一来源的其他章节。明确点名项目时可以聚焦该项目，泛化推荐问题则不会被单一文档的重复分块占满。

## 成本边界

- 修正后正式 60 题每题执行一次 A 版和一次 B 版查询，共 120 次查询向量调用。
- 修正后先对原 10 个失败执行 10 次 B 版查询，再执行 12 题 A/B 安全回归，共 34 次查询向量调用。
- 文档重新向量化调用：0。
- 文本生成调用：0。
- 新增索引或存储：0，继续使用现有 68 份文档和当前活动代际。

当前 Embedding 客户端没有向实验接口返回 token 或账单金额，所以本轮能精确记录调用次数和延迟，不能给出供应商实际费用。下一阶段需要在模型调用层持久化输入字符数、token、模型名、供应商 usage 和失败重试次数，才能比较真实单次成本。

## 后续验收顺序

1. 由业务人员独立编写至少 60 个不直接照抄项目名和资料措辞的盲测问题，并标注可接受来源与不可接受来源。
2. 在现有 Recall@8 之外增加 MRR、nDCG、来源多样性和回答事实支持率，避免仅凭“进入前 8”掩盖第一名质量问题。
3. 在模型调用层持久化输入字符、token、供应商 usage、费用和重试次数。
4. 在生产等量副本上持续双跑，观察错误率、P95、供应商限流和索引更新稳定性。
5. 独立盲测达到约定门槛后，再灰度接入少量用户入口；当前 A 版继续保留。

修正后的原始结果见 `benchmark-v1-result.json`，原 10 个失败在修正后的实际排名见 `benchmark-v1-failure-diagnostics.json`，评测题集位于服务资源 `rag-b/evaluation-benchmark-v1.json`。
