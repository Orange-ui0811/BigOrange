# 智能分析接入 A / B 知识库：内容、成本与耗时实测

2026-10-03，8 类合成需求 × A/B × 2 轮，32 次真实生成，全部完成。使用当前完整索引，复用智能分析真实后端生成链路。普通入口仍使用 A，未替换知识库、未改客服模型、未保存测试用户历史或扣除平台积分。

**结论：保留智能分析旧策略、直接接入 B，尚不能获得全面收益。B 改善了部分推荐素材和重复稳定性，但本轮更慢、更贵，而且两版都存在事实支持和用户基础适配问题。B 的优势被旧关键词过滤、业务候选混入和过度压缩证据限制，不能据此判定 bge-m3 本身劣于 A。**

## 1. 实际测试对象

两边生成模型均请求 **Gitee `DeepSeek-V4-Pro`**，配置来源为后台 Redis 中的 `project`，不是客服 Flash，也不是环境变量中的 DeepSeek 官方 API。使用原智能分析 Prompt、温度 0.25、max_tokens 4096；未显式指定 thinking，供应商返回思考 Token。

| 配置 | A | B 实验接入 |
|---|---|---|
| Embedding | bge-small-zh-v1.5，512 维 | bge-m3，1024 维 |
| 分块 | 旧知识库已有片段 | STRUCTURE_M3_512_768_64_V1 |
| 向量条目 | 5,647 | 8,660 |
| 文档状态 | 491 篇 DONE，另 81 篇 PENDING | 565 篇 READY |
| 检索 | 原智能分析检索与融合 | B 原生 HNSW 混合检索，经实验适配接入 |
| 给生成模型的知识证据 | 最多 3 个项目、共 1,100 字符 | 相同上限与卡片压缩方式 |
| 学习／职业业务候选 | 保留 | 同样保留 |

这是当前完整部署方案对照，不是“相同文档、只换 Embedding”的消融实验。B 文档覆盖更多；也仍受原智能分析的后置关键词过滤限制。详细执行方法见 [protocol.md](protocol.md)。

## 2. 耗时与费用

| 指标 | A（16 次） | B（16 次） |
|---|---:|---:|
| 调用成功 | 16/16 | 16/16 |
| 平均完整请求耗时 | **39.89 秒** | **62.44 秒** |
| 中位耗时 | 36.63 秒 | 64.73 秒 |
| 最慢请求 | 86.64 秒 | 99.31 秒 |
| 平均检索耗时 | **0.58 秒** | **1.47 秒** |
| 平均模型调用耗时 | 39.15 秒 | 60.82 秒 |
| 平均输入 Token | 944 | 918 |
| 平均输出 Token（包含思考） | 2,107 | 3,498 |
| 其中平均思考 Token | **1,465** | **2,777** |
| 单次生成费用：统一标价估算 | **¥0.0619** | **¥0.0950** |

| 折合 1,000 次同类请求：统一标价估算 | 约 ¥61.90 | 约 ¥94.96 |

本轮 B 平均耗时增加约 **56.5%**，按统一标价估算的费用增加约 **53.4%**。两版合计生成费约 **¥2.51**。

增量主要在生成阶段：检索只增加约 0.89 秒，模型阶段增加约 21.67 秒；B 输入 Token 反而略少，额外输出 Token 中约 94% 来自思考 Token。**不能把整轮更慢解释成 HNSW 慢，也不能把费用增加解释成 bge-m3 收费更高。**

费用按请求 SKU `DeepSeek-V4-Pro` 的公开标价输入 12 元／百万、输出 24 元／百万归一化估算。A、B 各报告 1,024 个缓存命中 Token，表内仍统一按普通输入价计算；缓存优惠、资源包折扣和实际账单未核验，因此不是实扣金额。思考 Token 已包含在输出 Token 内，没有二次收费相加。[Gitee 公开模型价目](https://ai.gitee.com/serverless-api?model=DeepSeek-V4-Pro)

Gitee 官方目前声明已部署 Embedding 免费；本轮未重建索引、未翻译入库。已有入库费用、服务器、存储与运维未计入上述金额。接口没有给出完整 Embedding Token 用量，不能声称消耗为零。[Embedding 官方说明](https://ai.gitee.com/docs/products/apis/embeddings/)

### 供应商返回标识的影响

虽然请求配置相同，供应商返回了 `deepseek-v4-pro` 与 `deepseek-v4-pro-ga-260813` 两种标识。A 分布为 10/6 次，B 为 4/12 次，因此总体差异不能完全归因于 RAG。

进一步只保留**同一道题、同一轮、返回模型标识一致**的 10 对请求：

| 指标 | A | B |
|---|---:|---:|
| 平均耗时 | 45.41 秒 | 59.33 秒 |
| 平均统一标价费用 | ¥0.0722 | ¥0.0890 |

这个子集中，B 仍慢约 **30.7%**、贵约 **23.3%**。它减轻了模型标识混杂，但不是固定权重、固定服务节点的大样本因果实验；不能承诺未来每次都会出现此差距。

## 3. 内容差距

| 需求 | A | B 直接接入 | 结论 |
|---|---|---|---|
| Java 新手学 Spring Boot | Nacos、Embabel 示例，偏中高难度 | Java 项目式教程、Spring Boot 认证练习与 Embabel 示例 | B 主项目更适合入门，但部分描述超出了证据 |
| RAG 求职项目 | Dify + Chatchat／Promptfoo | Pathway LLM-App + Quivr／Dify | B 更偏端到端问答，多源接入事实更具体；两版均未充分确认 Java 改造成本 |
| Python，中文查英文资料 | Pathway + Dify | Quivr + TypeScript 的 LLM-Hub | A 的组合更贴近 Python RAG；B 的 Quivr 依赖更具体，但第二项偏离核心需求 |
| Agent，小团队商业工具 | 教程／Dify + MonkeyCode | Dify + Agent Teams AI | B 更贴近协作产品，但商业价值与交付周期仍只是建议 |
| Vue 新手演示项目 | ASF 配置生成器为主，第二轮减少为一个项目 | ASF + Protocol Launcher | 大多来自共同业务候选，换库收益有限；B 仍可能给新手增加高阶负担 |
| Python 数据分析求职 | 第一轮无项目，第二轮 Doris + Kibana | 两轮都是 Doris + Kibana | 两版均有语言、规模与基础适配问题；B 更多推荐不等于更好 |
| 3D 打印，切片或控制 | Slic3r + Mainsail | 镜面阵列生成器 + Mainsail | A 更直接覆盖切片与控制；B 的第二方向变成模型生成 |
| 明显缺少资料的苛刻需求 | 两轮空推荐并说明不足 | 两轮空推荐并说明不足 | 本轮两版均未编造仓库 |

所有 **25 条 A 推荐、28 条 B 推荐**都能绑定到当次知识或业务候选的仓库 URL。但这仅是身份绑定成功，**不是回答准确率 100%**。例如 B 的一条证据仅有 “Spring Boot Integration Architecture”，生成却写出了消息通信、任务调度等具体能力；A 也出现未由当前证据支持的跨语言能力、模拟模式等说明。

两轮同场景送入模型的知识证据文本哈希全部一致。最终项目集合完全一致的场景：A **4/8**，B **7/8**，均含一个两轮空推荐场景。B 在这组小样本中更稳定，但稳定推荐 Doris/Kibana 给 Python 数据分析用户仍不等于推荐合理。

详细逐项评审与原句定位见 [content-review.md](content-review.md)，完整输出见 [outputs.md](outputs.md)。本轮没有独立人工金标准或 RAGAS 评分，不虚构 Recall、MRR 或回答正确率。

## 4. 为什么 B 没有直接带来全面提升

1. **旧查询没有明确告诉 B“要推荐项目”。** 原生 Top8 可能被同一仓库多个片段占据。数据分析例子中，TheAlgorithms/Python 一度占 5 条。
2. **旧关键词准入继续约束语义检索。** 数据分析的 B 原生检索两路均有候选，经旧主题／身份过滤后，给生成模型的知识证据变成零条。它不是 Embedding 调用失败。
3. **强压缩丢失了 B 的长文档价值。** 每项目压缩到约 220／360 字符，总计不超过 1,100 字符，某些候选仅剩标题或零散技术词；结构分块得到的章节没有完整进入生成。
4. **独立业务候选仍能左右输出。** A 的 25 条推荐中 11 条来自学习／职业业务候选，B 的 28 条中有 13 条。知识检索为空时仍可能生成真实但不够适合用户的项目。
5. **身份绑定没有覆盖事实支持。** 当前 URL 绑定无法核实所有功能、难度、完成周期和商业判断。模型思考更多也不会自动补齐缺失证据。

实验结束后另做一次不生成回答的诊断试搜：数据分析查询显式加入“推荐项目”后，经同样过滤的 B 证据由 0 个项目变为 1 个 `vinta/awesome-python` 资源清单。说明意图与候选多样化确实影响接入，但一个资源清单仍不是完整的项目推荐方案，不能当作质量修复已完成。该试搜不计入 32 次生成及费用均值。

## 5. 后续建议与交付边界

建议继续以 B 作为改造基础，但先适配智能分析的推荐编排，再决定是否替换 A：统一真实候选与硬条件检查 → 显式推荐意图、项目去重和章节聚合 → 提供含语言与依赖的最小事实包 → 区分事实与建议并校验支持 → 固定生成版本与思考预算重测。

不要仅把检索接口指向 B 就认定升级完成。也不要在下一轮同时换模型、放大 Prompt 和改排序，再把全部收益归因于 B。

索引资源方面，Redis 报告的向量索引占用 A 约 **13.98 MiB**，B 约 **39.05 MiB**，约为 **2.79 倍**。这是索引计数器，不是整个 Redis 进程内存或服务器费用；本轮没有持续负载或容量测试。

验证记录：实验入口与用量记录相关 **14 项测试通过**；未登录调用实验入口返回 **401**；实验前后模型配置、索引规模、文档内容统计校验及运行代码哈希一致。32 次生成无失败，无自动重试；原智能分析入口继续使用 A。
