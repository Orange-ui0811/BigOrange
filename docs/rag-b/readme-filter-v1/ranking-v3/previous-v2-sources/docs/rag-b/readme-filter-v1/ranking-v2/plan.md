# 项目内证据排序改进 V2

2026-10-31。用户要求继续改进，先修复已观察到的同项目名称排序干扰，再用冻结问题进行受控验证。

## 修改范围

新增 `RagBProjectEvidenceScorer`：显式项目名仍获得同一个 0.1 项目加分；项目内部只使用向量排名和权重 0.2 的正文关键词 RRF，取消名称通道片段序号加分。仅名称匹配而没有正文或向量依据的候选得 0 分。`RagBRedisStackRepository` 使用新评分并在 trace 标明策略。旧 `RagBFusionScorer` 保留供既有验收和本轮对照。

本轮不升级框架、改变模型、重做分块、重建或激活索引。没有按照失败题 ID、项目名、预期答案设定排序例外。实际生产 Repository 的 Redis 集成测试通过后，代码可在后续重启后端时生效；本轮只运行隔离测试，不启动业务后台。

## 公平验证

沿用首轮封存的 28 题、标注和两组实际索引：86 个原文块与 28 个知识块。读取时核验 Redis 文本与冻结 corpus 相同，复用所有文档向量。

每题查询向量只生成一次，每组检索三次；每次保存完整向量／正文／名称召回候选、原始排名和相似度。同一候选同时应用 LEGACY_RRF、PROJECT_CONTENT 和 SCOPED_CONTENT。最后一种只保留候选中显式匹配的项目，是额外的硬范围消融，不自动用于网站。

28 条查询＋1 次预热，计划29次本地推理，独立30次上限账本，失败计数，无自动重试；不占用旧分类额度或旧检索账本。保存查询向量用于后续无需推理的重放。只调用固定摘要的本地 BGE-M3，没有云端模型或密钥。

复用专用 `orangejd-readme-retrieval-v1` Redis 容器，未映射宿主端口。主要消融只读既有测试索引；另行启用真实 Repository 集成测试，在该容器中创建随机 it 前缀的临时索引，完成过滤和并发验证后只删除其自有键。业务 Redis 与 MySQL不参与。

## 验收和范围

- 新评分单元测试验证实际观察到的名称序号逆序、项目名保护、仅名称无正文、无项目名时的兼容行为和多项目比较。
- 现有 B 搜索服务、相关性判断和旧评分回归通过；真实 Redis 集成测试不得以跳过冒充通过。
- 22 道有证据题分别统计首位项目命中、前5片段项目命中、前5片段必要原文完整。每个候选策略使用同一证据覆盖评分；6 道不足题不伪装成已正确拒答。
- 复验旧分类、分块、检索首轮产物和新输入／结果哈希，保留新旧全部输出。

样本曾用于调试、标签来自助手，属于诊断回归而非独立人工评测。小样本延迟不等于客服端到端耗时。排序改善不能替代条件追问、事实充分性判断、证据核验与业务 projectId／导入资格校验。

## 证据不足时的处理边界

当前客服已有生成后引用检查和模型事实核验，但 B 检索的 `answerPolicy` 仍以章节数／字符数作粗门槛，不能据此证明事实齐全。下一步设计需要区分：用户未提供的决策条件可以追问；知识库没有证据的项目事实应标待核实，不能通过追问让用户替系统确认未验证事实；存在原文且本轮未召回的证据应先回查。

这轮先验证检索排序，避免一边改召回一边改变证据充分性标准，使改进无法归因。不会宣称已实现完整自动追问或正确拒答。
