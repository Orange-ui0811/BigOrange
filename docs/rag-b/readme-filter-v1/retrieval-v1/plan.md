2026-10-31。本轮实施用户已同意的下一步：冻结问题和原文证据，对比旧结构分块与新知识单元分块。不切换网站活动索引，不执行正式 K4 生产激活。

## 冻结输入和对照

- 使用上一轮 5 个仓库的完整冻结 README 与分类、分块结果。原文基线调用项目现有 `RagBTokenChunker`（512 目标、768 最大、64 章内重叠）；知识组使用 28 个已生成的最终 Embedding 文本。
- 28 道固定问题：22 道有可用证据、6 道缺证据。覆盖用途、架构、安装、版本、许可、限制、多步骤条件和不包含项目名的需求。助手标注，既有已调试样本，不冒充盲测。
- 每题预期项目按 documentId／仓库标识判断；证据由冻结原文块 ID、完整区间、原文和行号标注。相同命令的有效原文位置可作为备选证据。
- 在第一次推理前冻结 corpus、问题、原文与 Java/Python 实现哈希。结果不因未达预期而重新抽样或覆盖前序版本。

## 本地运行

只使用本机已下载的 `bge-m3:orangejd-v1`，固定摘要 `sha256:7907646426070047a77226ac3e684fbbe8410524f7b4a74d02837e43f2146bab`，1024 维、禁止截断。复用 Java `RagBOllamaEmbeddingModel`；无任何云端模型地址或密钥。

本轮本地推理最多 50 次，独立账本；预计次数为 1 次预热＋去重正文每批 8 条＋28 条单题查询。失败也计数，不隐藏重试；超上限停止。之前 18 次分类额度完整保留，不用于本次实验。

创建专用 Redis Stack 容器 `orangejd-readme-retrieval-v1`，256 MiB 上限，无宿主端口映射，不挂载业务 Redis 数据目录。两组索引位于 `orange:rag:b:experiment:readme-retrieval-v1-20261031:` 前缀。Java 验证进程只共享该测试容器网络，并通过 Docker 的宿主机地址调用本地模型。不启动业务 Spring 上下文，不连接 MySQL，不触发自动同步。

## 检索和证据

两组统一使用 Redis HNSW 向量、正文关键词、名称三路召回，候选上限 128，TopK=5，向量阈值 0。复用平台 `RagBQueryTokenizer`、`RagBFusionScorer`（RRF，正文权重 0.2，显式名称门控）；Spring AI 存储使用独立的实验元数据模式，来源片段在冻结 corpus 中保留完整映射。未直接调用生产 `RagBSearchService`，也未包含其后续多样性与业务过滤，本轮属于召回层验证。

本轮没有 cross-encoder、LLM rerank、查询改写和客服回答模型。原文基线直接使用命中块；知识组另统计命中父单元后补齐证据的结果，不从原文回填 REVIEW 或未读导航内容。

## 指标和局限

分别统计项目命中@1/@3/@5、Top5 直接证据完整、父单元回查后证据完整。证据完整要求每个必要证据组至少有一个完整原文区间被覆盖，不能仅凭项目名命中算通过。

每题每组检索三次，交替两组执行顺序。查询向量只生成一次并共享，Embedding 耗时单独统计；检索 P50/P95 只涵盖 Redis 三路召回和融合，不解释为完整客服响应耗时。只有 5 个仓库，不能推断生产规模性能。

缺证据问题用于观察召回风险：当前召回层通常仍返回候选，这不等于项目能满足要求，也不等于已实现正确拒答。拒答、合理追问、条件匹配和业务资格需要后续客服链路验收。没有业务 projectId 映射时不能认定项目可导入。

原文与知识组同时改变准入、语义分组和检索前缀；这是整体方案对照，不能声称只测了分块长度影响。K3 已知许可／范围问题保持可见，不借检索结果改变正式激活门槛。
