## 下一轮首先验证的排序问题

当前复用的 RRF 会在显式出现项目名时，加入 `3/(60 + nameRank) + 0.1`。同一仓库下所有片段的 title/sourceRef 基本相同，名称通道产生的先后位置可能不反映这次问题需要的内容。

实际例子：R18 的 Docguard 通用示例块向量排名第 6、名称排名第 2，最终排到首位；参数说明块向量排名第 2、名称排名第 8，最终仅列第 5。这证明当前融合存在“名称靠前的通用片段压过更相关向量片段”的情况。它与这轮漏证据现象一致，但尚未用完整候选消融量化全部影响，不能把 6 个失败都未经验证地归因于一个参数。

建议下一轮保留当前结果，增加受控对照：先识别或召回项目，再在该项目内按问题相关性选证据；名称用于确定项目，不把名称检索的任意片段先后当成内容相关性。导出全部三路候选和融合前后排名，对比现有 RRF、移除项目内部名称排名、项目范围内检索。先固定现有模型和分块，再决定是否引入 rerank 模型，避免同时改变多项因素。

## 还不能发布的业务能力

6 道证据不足题在两组中全部仍会返回候选。召回层可以返回相似文本，却没有证明能回答该问题。本轮没有客服回答模型，因此不能把这些结果当作错误回答，也不能宣称系统已经正确拒答。

例如 4096 的错误排障堆设置不能直接推出生产机器最低内存；未批准的 VITE_PORT 说明不能通过回填原文绕过 REVIEW；n8n 混合许可仍未解决，不能凭项目名或文档链接给出商业使用结论。

后续还需要答案前的证据充分性判断：有明确事实才回答；存在影响选择的条件缺口时追问；知识不足时说明未核实并提供合适的后续路径。业务 projectId、项目状态和导入资格仍需正式链路核验。

当前最优先的工作是项目内证据排序和证据充分性判断。继续增加块数或把这轮命中率解释成完整客服效果，都不能解决已观察到的失败。

## 产物与复验

- `cases.json`：冻结问题与助手标注的原文证据。
- `corpus.json`：两组实际索引文本及原文映射，知识组同时保存父单元证据。
- `retrieval-results.json`：28 题、两组、每组 3 次真实 Top5、三路排名和分段耗时。
- `evaluation.json`、`report.md`：首轮评分及报告，保持原样。
- `local-embedding-calls.jsonl`：独立本地推理账本，44 次。
- `completion-seal.json`：首轮结果封存哈希；`analysis-seal.json` 另行关联本分析和评分测试，避免改写首轮封存结果。

运行 `python scripts/readme_chunk_retrieval.py verify` 可以只读复验首轮结果。测试索引保存在专用容器 `orangejd-readme-retrieval-v1` 中，无宿主端口和业务数据目录挂载；停止、移除测试容器或改变内存数据不会切换网站活动索引，封存文件仍可追溯本轮结果。
