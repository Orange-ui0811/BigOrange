## 新提示词并不覆盖所有待审内容

实际调用 Java 当前 planner，分别导出了 max4 和 max8 的完整请求。新增 1 项无网络规划测试通过，核对私有依赖单元与公开 `plan` 输出完全一致；传输接口若被调用会直接失败。

| 原 29 条在新版中的位置 | 每批最多 4 块 | 每批最多 8 块 |
|---|---:|---:|
| 实际模型目标 | 14 | 20 |
| 因单元超出目标数而跳过 | 6 | 0 |
| 组件含硬待审依赖，整组不发送 | 5 | 5 |
| 由规则／最终准入处理 | 3 | 3 |
| 来源自身硬待审 | 1 | 1 |

仅出现在 context 不算被模型分类。全 12 仓库共有 108 个需要模型处理的目标，max4 规划 79 个、跳过超限 11 个、硬依赖阻断 18 个；max8 规划 90 个，18 个硬依赖目标仍不发送。

max4 的容量跳过分别是 Flowise 的 6 目标单元和 Docguard 的 5 目标单元；这两组输入保守上界均低于 12000。因此可以用已支持的 max8 参数作试跑配置，不必增加真实重试或修改分母。

归因还确认了三个试跑前应修复的程序缺口：

1. Flowise 的 `</details>` 被当成代码前提，连带挡住 18 个待模型目标。
2. n8n 的许可证导航被当成全局 guard，导致 7 条知识因“导航不能进正文”而连带阻断。
3. Appsmith 的引导句、安装目录表由固定规则直接进入正文，V5 不会收到这两个目标。

具体位置、修复边界和验收条件见 [确定性修复队列](fix-queue.md)。当前决定是先修这些程序问题，再重规划、确定额度并真实试跑。

## 标签补全带来的真实口径变化

原 147 条文件及评分未改。新版本 [reviewed-labels-v3.json](reviewed-labels-v3.json) 保留原有判断，纠正 1 条理由并新增 2 条助手标签：

- `Q2-240-52` 保存原句完整，旧“破折号后截断”理由不成立；整块定位与绝对承诺混合，保持 REVIEW，理由纠正不带来分数提升。
- `S1-522-34` 为非独立的使用方式引导句，作为有效但尚不能单独使用的配套上下文待审。
- `S1-522-39` 为安装文档目录，标签与地址进入导航，不当作安装步骤。

扩为 149 条后，原先未计分的两个实际正文候选纳入分母，精确率为 **53/56＝94.64%**；原 147 条口径的 **53/54＝98.15%** 继续保留。代码没有变化，两个结果的标注覆盖范围不同。知识恢复率仍为 53/82；新增两条没有被加到 B 类恢复率分母。

详见 [标签复核](label-review.md) 和 [扩展口径评分](supplemental-evaluation.json)。这些标签是观察输出后的助手复核，不是盲测或独立人工金标准。
