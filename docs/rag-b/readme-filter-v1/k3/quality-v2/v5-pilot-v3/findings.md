## 发现一：开发步骤缺少必要配套信息

- 案例：Flowise `Q2-244-155`，“6. 开发构建：”。
- 必要原文：第 157 行，“在 `packages/ui` 中创建 `.env` 文件并指定 `VITE_PORT`（参考 `.env.example`）”。
- 模型给引导句 KEEP，却将配套说明 REVIEW；当前依赖图主要绑定代码及代码说明，没有把这个“引导句＋缩进的普通操作说明”成组，导致前者独立进入正文。
- 原文 ID 和引用正确，不代表步骤完整；这正是精确率分母中 1 条不合格正文的原因。

**下一步优先补依赖**：在 `ReadmeKnowledgeFilter.dependencies` 识别这类非代码配套步骤；任一必要部分未获准时整组待审，均获准时一起入候选。新增真实原文和反例测试，继续保护纯导航隔离、独立事实和共享前置条件分批机制，不按项目 ID 打补丁。

## 发现二：命名故事被误当运行限制

`V16-427-03` 首轮和预留重试均为 `OUTPUT_REJECTED_PROTECTED_DROP`。进一步核对后，冲突的是 n8n 第 73 行命名故事，里面说“无法想象每次在 CLI 中都要输入那么长的名字”。

- 规则因“无法”等措辞给它固定 KEEP／CONDITION_OR_NEGATION。
- 模型判 DROP，与冻结标签的命名噪声判断一致；固定 KEEP 不允许模型改成 DROP，因此整批被拒绝。
- 这是程序保护的误判，不应描述成模型要删真实运行限制。当前拒绝机制遵守了契约，但前面的内容判断仍需修正。

**下一步修内容判断**：让“名称含义／命名由来”等标题和叙述共同判定命名故事，避免仅凭“无法”等词把故事当约束。同时回归“无法连接 Redis”“必须保留版权”等真实限制；不能直接放开所有固定 KEEP 的删除权限。

另一处首轮失败是 `V16-546-03` 的 `OUTPUT_REJECTED_EVIDENCE`：模型复制一个上下文 ID 时写错字符。整批未采用；相同输入的唯一预留重试通过。保留严格 ID 校验，不用模糊匹配替换错误引用。

## 性能与边界

提供方返回的累计 usage：输入 55875、输出 13941、合计 69816 tokens，包含校验失败的响应。未换算费用；输入预算的 UTF-8 代理与实际 tokenizer usage 分开保存。

此轮只检验 README 分类与最终准入，没有测试向量召回、rerank 或网页客服推荐效果。7 个其他仓库没有执行本轮新提示词，不能将它们的旧选择与这 5 个新结果合称统一版本真实验收。
