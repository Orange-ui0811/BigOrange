## 发现的实现问题

### 1. 导航解析失败后会错误回落到正文

`ReadmeRecommendationProjection` 的链接提取只处理 Markdown；当模型已经识别 `SOURCE_POINTER`、但 HTML `<a href>` 没被解析出地址时，分支仍可能满足 IN_SCOPE＋非 OTHER，落入正文。

- `Q2-240-23`：AnythingLLM 文档 HTML 链接。
- `Q2-240-26`：托管实例 HTML 链接，应为相关产品导航。
- 模型这两条都返回 SOURCE_POINTER，错误发生在最终准入，不是只改提示词就能解决。

修复方向：安全解析 Markdown/HTML 的标签与原始地址；SOURCE_POINTER 无论能否解析出地址都禁止进入正文。解析不足时留复核，不读取链接目的页。导航不应继承正文的全局条件阻断。贡献入口 `Q2-427-63` 和 Appsmith `Q2-522-36` 也要补回归。

### 2. 条件识别与全局依赖过宽，导致整库误阻断

当前规则对原始字符串匹配 `only`、许可、硬件及否定词，再把所有 guard 应用于全部正文。URL、图片属性和一般叙述都可能触发。

- Flowise 图片地址 `#gh-light-mode-only` / `#gh-dark-mode-only` 被标成 LIMITATION，尚未获准时触发全局依赖阻断。该库 33 条应恢复正文，本轮恢复 0 条；其中 27 条最终原因为 `DEPENDENCY_NOT_ADMITTED`。
- n8n 命名故事中的“无法想象……”被标为限制，一般叙述不应成为全项目的部署要求。
- 图片或徽章内的 CPU/GPU/许可字样也不能直接变成已核验的适用条件。

修复方向：先区分可见正文、地址、图片和装饰；区分真正的项目级许可、局部安装条件、可选方案及普通叙述。依赖按项目／使用方式／章节或示例的实际作用域关联。保留真实约束；不能为提升恢复率一并移除全局许可保护。

### 3. 徽章、截断与产品混合仍能绕过复核

- AnythingLLM、IoT、Docguard 的许可徽章被当成正文许可证据，目的页未读取。
- `Q2-248-35` 的 Milvus 最后一句停在 `cli`，规则未命中截断，且没有模型提案也以规则证据进入正文。
- `Q2-248-22` 同块描述 Milvus 与 Milvus Lite，最终被统一归 CORE。

修复方向：图片/徽章证据强制与正文许可分离；文档末尾和不完整句子独立检查；无法给整块明确产品归属时复核，后续以有位置映射的更细原文块处理。不要仅扩充某几个固定产品名来拟合本集。

### 4. 仓库资格仍容易被局部知识绕过

- awesome-selfhosted 的有效资源集合说明进入正文，`Q2-426-5/7` 应保留归档，不能成为该仓库的可部署功能证据。
- Marlin 配置集合在当前原文不足以证明可推荐源码模块时仍被放行，版本匹配条件也被标为 CORE。

修复方向：建立可追溯的仓库／具体组件资格证据，默认 UNKNOWN；模型只能基于本次原文判断。混合仓库允许有依据的源码部分参与，纯资源集合和资格不明的配置包不能借一个局部段落自动升级成项目候选。

### 5. 语义依赖与结构依赖还没有衔接完整

- Docguard `Q2-546-82` 使用 `--fail-on/--ext` 的命令、`Q2-546-96` 的退出码说明，没有在相同候选携带 `Q2-546-63` 的参数与默认值原文。
- `Requires Go 1.22+` 原文保留，但最终只有 PLATFORM_SPECIFIC，没有要求的 VERSION_SPECIFIC。

修复方向：补可校验的语义依赖；候选组包要携带条件及解释，不能只有引用 ID 或散落在另一个候选。模型证据引用与“用户必须满足的条件”要分开；替代方案不能错误变成需要全部执行的要求。版本、平台和产品归属可以并存。

### 6. 噪声的类型协议仍有稳定失败

`R5-427-04` 两次均把命名故事标为 `KEEP + OTHER`，违反冻结协议。整批拒绝机制正常工作，但同批贡献导航也只能待审。重试没有解决；本轮没有更改提示词后重新抽样。

修复方向：下版补充 OTHER 的明确边界及命名故事反例；与“只因语义不满意就重试”区分。若修改协议或提示词，必须建立新版本，不能替换本轮成绩。

## 下一步的实施顺序

1. 回到 R3，先用这些真实原文和已保存响应写失败回归，优先修导航错误回落、徽章放行、URL 触发全局 guard。

## 测试、执行与局限

新增 14 项评分器边界测试和 2 项无网络 Java 执行测试均通过；34 个真实请求的 system/user 与冻结内容相同，实际 HTTP 与选择器各有独立持久账本。所有仓库的批次结果已合并，首轮文件及 R4/旧账本哈希不变。没有访问 README 链接或执行其中命令。

再次运行同一首轮入口，全部已预留批次被跳过，新增真实出站 0，累计仍为 35；首轮封存文件保持不变。该检查验证了正常完成后的去重，不代表已经模拟进程在任意指令位置崩溃的所有场景。

首轮单次分类耗时 1.08–4.30 秒、平均 2.69 秒；提供方报告首轮用量 110568 Token。这是分类入库环节，不是检索或客服端到端性能。实际提供方计数与保守输入预留不混用。

标注均由助手按用户规则提前制定，属于目的性边界集；Flowise 的 33 条应保留知识占本集较大比例。这些比例只描述本集，不能外推为全库总体准确率。规则通过并不等于语义分类通过，本轮结果也不代表现有 B 版线上检索已经采用了这些过滤结果。
