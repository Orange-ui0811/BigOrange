# 智能分析 A/B 成本与耗时归因复测报告

执行日期：2026-10-03。结论：上一轮 B 成本与总耗时更高是有效的样本观察，但不能解释为“B 的旧流程适配问题必然增加思考”。本轮没有稳定复现该整体差距。可以定位的额外检索时间主要是 Embedding HTTP 和数据库元数据／业务有效性过滤；生成阶段是主要耗时及费用来源，其用量波动明显，返回模型标识也未冻结。

## 范围与结果

四题：Spring 入门、Python 跨语言 RAG、Python 数据分析、无匹配项目。24 次检索单测；8 次完整生成链路捕获；每个完整请求再重放两次，合计 24 次带知识生成；8 次去知识证据对照。32 次模型调用中 31 次成功，1 次输出截断失败。没有重试，没有补成功样本。

使用智能分析当前 Gitee `DeepSeek-V4-Pro`，不是客服 Flash。请求参数 `temperature=0.25,max_tokens=4096`，未显式设置 thinking；供应商返回思考用量。每个生成请求调用一次生成模型，没有 RAGAS、模型事实裁判或额外模型校验。完整生成路径调用两次 Query Embedding；冻结重放不进行检索或业务查询。

所有测试使用合成需求，不读取账号画像或聊天历史，不扣积分，不写趋势历史，不切换普通入口。开发接口需要管理员鉴权，未经鉴权返回 401。27 项关键回归测试通过；脚本语法检查通过。

## 生成差异的可核对证据

### 相同请求和同返回标识仍明显波动

无匹配项目首轮 A/B 的完整模型请求 SHA256 相同，返回标识同为 `deepseek-v4-pro-ga-260813`。模型耗时分别 18.42／31.09 秒，思考 Token 分别 577／1502。这一差额不能由不同 A/B 证据解释。

Spring 入门 A 的三个冻结请求哈希一致，返回标识全部相同。模型耗时 75.64／37.76／72.63 秒，思考 Token 3929／1926／4029，均次费用分别 ¥0.121152／¥0.065112／¥0.120168。仅固定检索和 Prompt 不能固定生成开销。

### 供应商返回标识未固定

请求始终使用同一 SKU 和配置版本，但成功的 A 请求返回 GA 标识 10 次、普通标识 2 次；B 分别 3 次、8 次。相同请求也出现不同标识以及不同输入 Token 统计。不能确认这些标识是否代表不同实际权重，也不能将两组混合平均数视为完全控制生成模型后的差异。

12 个预定 A/B 配对中，只有 4 对成功且返回标识一致。这一子集的模型均值 A 40.46 秒、B 56.60 秒，成功均次估算 A ¥0.064029、B ¥0.088077；思考 Token A 1709、B 2805，非思考输出 A 563.5、B 528.3。

在这个小子集中，B 的费用差额约 ¥0.024048，其中输入差额 -¥0.001410、思考差额 +¥0.026304、非思考输出差额 -¥0.000846。更多思考用量解释了该子集的费用差额，不是更长输入或更长正文。

但这四对包含上面完整请求完全相同的无匹配样本，而且按返回标识选取不是随机分组，样本很小。这个子集不能证明“B 适配缺陷导致多思考”，也不能忽略它只展示混合平均较低的结果。

31 次成功调用中，总输出 Token 与模型耗时相关系数约 0.986，思考 Token 与耗时约 0.967。它支持生成用量是主要观察因素，但相关性不单独证明内部原因；非流式响应不能拆分供应商排队、预填充、思考和正文解码时间。

### 去证据对照有影响，但不能作为降本产品方案

移除知识参考后，每题 A/B 剩余请求体一致。Spring 的无知识对照平均模型 13.05 秒、思考 358 Token；带知识 A/B 分别 62.01／59.11 秒，思考 3294.7／2656.7 Token。对照说明知识候选与推荐任务的内容可以影响生成开销，并非耗时只由输入长度决定。

但移除证据也改变了可推荐项目与回答内容，不能证明具体哪条过滤或压缩规则造成更多思考，不能为了降本删掉知识库。RAG 场景去知识对照平均 44.90 秒，反而高于混合版本 B 的 39.38 秒，说明并非知识越多必然越慢。

## 输出预算与失败统计缺口

某次 B 请求设置 `max_tokens=4096`，返回 `completion_tokens=5388`、其中思考 4909，`finish_reason=stop`。A 也有超过 4096 的完整返回。实测不能把该参数当作思考加正文的总费用上限，具体参数语义需要按供应商能力核实。

保留的 B 重放失败耗时 85.49 秒，根异常 `AI输出未完成: length`。客户端在读取 usage 前先拒绝不完整输出，导致该次用量与费用缺失。详见 [失败分析](failure-analysis.md)。没有将失败成本记为 0，也没有重试。

## 已排除、已定位与未证实

| 判断 | 当前证据 |
|---|---|
| B 多次调用生成模型或模型裁判导致差价 | 已排除；每项只调用一次生成模型 |
| B Prompt 更长造成费用增加 | 本轮不支持；完整请求平均字符 A 1841.75、B 1454.50 |
| 本地压缩、关键词过滤计算花了几十秒 | 已排除；相关本地处理毫秒级 |
| B 检索额外时间 | 已定位；主要是外部 Embedding，其次数据库过滤 |
| 更大生成用量导致较高估算费用 | 可按返回 usage 直接计算；思考用量解释同返回标识子集的差价 |
| 生成波动存在 | 已证实；同请求、同返回标识也能明显变化 |
| 返回标识差异干扰对照 | 已观察；内部实际版本是否不同未证实 |
| 压缩、关键词过滤或候选不一致导致模型多思考 | 尚未证实具体因果；它们是质量问题，但不能直接当成本原因 |
| 供应商排队、预填充或思考耗时占多少 | 接口缺少内部时间，无法确认 |

优先改进方向：保留分阶段监控；在完整性校验前记录全部返回用量；核实并控制供应商的思考预算和总输出预算；在固定实际模型能力与重复请求下继续比较；批量化 B 的元数据／业务有效性查询。旧证据适配仍应从回答质量修复，但其降本收益需要独立实验验证。客服 Flash 必须按自己的调用编排评测，不能套用本报告数值。
