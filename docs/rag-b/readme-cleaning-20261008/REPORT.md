# GitHub 原文预处理：完整 B 库对照实验

日期：2026-10-08。结论：**可以建立可追溯的整理副本，但不能把“删得更多”当成检索更好。保守整理提高了部分异常格式题的命中，尚未证明总体排名稳定改善，不切换现有索引。**

## 1. 本次实际做了什么

- 只读冻结当前 B 库 **565 份有效文档、8,660 个片段**；其中 **368 份 GitHub 来源文档**参与清理，其余 197 份保持原样，作为完整索引中的其他资料。
- 旧库有 375 条 GitHub 记录，其中 7 条有效正文为空，单独记录在 `legacy-github-scope.json`，不伪造内容或向量。这里的“原文”指数据库保存的正文，包含既有中文处理结果，不等同于重新抓取 GitHub 最新 README。
- 保存原始快照、每种整理副本、清理事件、质量提示、分块、向量缓存及原文定位映射。没有更新数据库正文、生产 Redis 或活动索引。
- 模型固定为本机 Ollama `bge-m3:orangejd-v1`，1024 维；模型 digest、活动代际及语料哈希见 `manifest.json`。
- 分块保持当前 512 Token 目标、768 上限、同章节最多 64 Token 重叠。实验 Python 复现与当前 **368/368 份 GitHub 文档的全部片段正文及顺序一致**，生成数量也一致。另保留 `stored` 实际库存片段对照，检索质量与 `raw` 相同。
- 两轮实验：第一轮原文、轻清理、广泛结构整理、删代码反例；看到回归后，第二轮增加保守整理。第二轮属于开发迭代，不能充当新盲测。

## 2. 各方案实际规则

数字和运算符、版本、否定词、警告/支持状态符号、代码、表格、普通链接和图片说明不按“符号噪声”一律删除。许可证、DOI、安全和基金会等有意义徽章需保留。首轮 `light/structured` 的引用式徽章规则较宽，只作为实验基线；保守候选另加相邻正文、警告与 HTML 语义保护测试，不建议直接把首轮清理器上线。

整篇围栏修复仅命中本次 Navidrome 文档：数据库把包含多个 Markdown 标题的整篇 README 包在 `html` 代码围栏中。删除外层包装，保留实际正文。普通 HTML 示例不会套用这个规则。

## 3. 评测设计与口径

冻结 172 道问题后再检索：

- 历史 140 题：50 道名称/来源回归、90 道语义表述题。其中 GitHub 语义题 30 道，来自 10 个事实，包含中英文和改写，并非 30 个独立事实。
- 新增 32 道格式探针：6 个仓库、16 个事实，每个事实有带名称和不带名称两种问法。覆盖 API、数值步长、格式回退、许可证、否定条件、风险提示、整篇错误围栏和短而有效的介绍。
- 现有题目、目标来源和事实关键词保持原样，冻结时检查所有目标事实仍在原文中，没有删除失效题来抬高分数。
- 单题继续使用原评测规定的来源类型范围；全部 565 份文档建入实验索引，但并非每题都跨所有来源类型检索。

**证据命中率@8**沿用历史 Recall@8 口径：前 8 条中存在目标来源，且同一片段包含要求的事实关键词；没有关键词的名称题只检查来源。它不是标注了所有正确项目的全面召回率，可能漏算同义证据，也不能证明回答事实正确。MRR@8 是首个合格片段排名倒数的平均值。

分别测精确余弦检索和隔离 Redis Stack 混合检索。混合复现参数：HNSW（M16、EF_CONSTRUCTION200、EF_RUNTIME10）、向量阈值 0.55、每路 128、融合 80、最终 8；RRF 常数 60，向量权重 1、正文关键词 0.2，明确名称命中时名称路 3 并加 0.1；复现同来源去重和推荐问法的来源分散。

实验 Redis 独立运行在本机 6381，使用与现有服务相同的镜像。实验完成后已核对标签并移除本轮容器，数据包与报告保留，见 `isolation.json`。索引为 HASH，而平台为 Spring AI 的 JSON 索引。这里是**检索核心复现**，不是实际 Java 客服接口调用：没有跑权限、业务条件过滤、数据库项目有效性、生成及引用事实审核。结果不能代替平台完整上线验收。

保守方案全部 172 题证据命中从 **157/172 到 159/172**，但 MRR 从 **0.7535 到 0.7517**，不是全面胜出。按仓库聚类重采样（15 仓库、62 道带事实 GitHub 题）得到 MRR 差值的探索性 95% 区间约 **[−0.0408, +0.0376]**，跨过零；不足以证明稳定总体提升。

具体变化：

- Navidrome 的“个人音乐收藏服务器”和“为什么选 releases 而不是 master”两道不带名称的问题，保守整理后进入前 8；错误外层围栏修复使说明与警告更容易成为独立证据。
- 同一项目某些带名称的题排名下降。拆出更多章节后，名称路加分可能让相关性不同的章节一起进入前列，说明**清理、分块、项目名称加分和章节排序存在相互作用**。
- 广泛整理使 LangGraph 的 durable execution / human-in-the-loop 两道英文题从命中变成未命中，事实没有被删，问题出在片段/排名变化；保守方案保持命中。
- 删除代码导致 `gui.addColor`、滑块步长、`onChange`、`minify` 和音频格式回退等 5 个事实的 10 种问法失去原文证据。省下 Token 的代价是真实功能信息损失。
- Slicer 的徽章很多，但仍有实际功能和平台支持说明，不能将“徽章占比高”直接当成无用项目。

逐题变化与前后命中来源见 `hybrid-paired-changes.json`，完整排名见各 `hybrid-*.json`。

## 6. 原文追溯、数据包与卡片边界

保守方案已生成 368 份统一 JSON 数据包和 Markdown 整理副本，包含：

```text
documentId / sourceRef / versionId / 原文哈希
清理后正文 / 清理后哈希 / 质量提示 / 建议资料类型
片段：章节路径 / 内容类型提示 / 位置 / 片段哈希
原文范围：Unicode位置 / Java UTF-16位置 / 原文行号
五项卡片字段的使用约束
```

5,589 个保守整理片段全部完成映射验证，涉及 6,104 个原文范围；新增字符仅允许分隔空白。**跨多个范围拼接的内容不能伪装成一段连续原文引用**，生成引用应分别回查原始范围。

扫描 Markdown 解析器识别到的代码/行内代码：保守方案 8,155 个原有代码范围未改写（单独排除明确修复的 Navidrome 整篇外层围栏）。这是当前样本的代码保护检查，不是对任意非标准语法的通用证明。8 项清理器回归测试通过。

五项卡片需要区分事实与建议：

| 卡片问题 | 数据使用规则 |
|---|---|
| 项目是什么 | 取真实介绍、功能和用法证据；原文没有的功能标记未知 |
| 为什么推荐给你 | 查询时结合用户确认条件与项目事实；不提前编造固定个性化理由 |
| 适合什么岗位 | 结合岗位资料与项目能力依据；清洗 README 不会自动证明岗位匹配 |
| 建议你做什么 | 跑通、改造、实现模块或贡献等明确标为实践建议，不能说成原项目现成功能 |
| 能证明什么能力 | 写可展示交付物与验收方式；不能把“建议完成”当成用户已具备能力 |

资料类型提示仅用于后续治理，没有偷偷改变本次检索过滤：README 路径指针应补抓被指向文件；资源合集应标为目录/集合，避免拿集合中的功能当成仓库本身；空正文与只有“个人博客”的记录需要补充资料。**清理不能凭空补出技术要求、周期或岗位证据。**

## 7. 成本、性能与未覆盖项

- 实验仅调用本机 Ollama：827 次批请求，3,304 个新增文本向量（含问题），0 次失败；其余向量按模型 digest＋内容哈希复用现有本地索引。
- Ollama 返回的累计输入统计为 736,194 Token，批请求耗时累计约 59.97 秒；这不是全部预处理、导出、建索引和评测的总墙钟耗时。
- 外部 API 调用 0，外部 API 费用 ¥0。硬件折旧与电费没有测量，金额 UNKNOWN，不能把本机运行称为总成本为零。
- 保守方案 GitHub 入库片段 Token 减少 5.12%、片段减少 101；不等于客服生成费用减少 5.12%。用户侧 Prompt 长度与真实回答调用尚未对照。
- 隔离混合查询 P95 约 19ms；这些数字不含实时 Query Embedding、Java/数据库检查、网络与生成，也没有做持续容量测试。小差异不足以宣称响应更快。
- 没有调用生成模型或 RAGAS。本次验证内容保存、检索与引用位置映射，**没有验证最终五项卡片的事实准确率、岗位匹配率或用户条件满足率**。
- 样本是历史开发题与源文档编写的格式探针，存在同事实多种表述；并未建立新的独立用户盲测集。

## 8. 本轮决策

1. 保留保守整理的数据包作为下一步接入候选，原文作为权威证据源，所有处理可回查。
2. 不上线广泛去 HTML、整段删代码或统一删除符号的方案。
3. 当前没有一个清理方案在命中、排名、全部题型上全面胜出，因此不直接替换现有 B 索引。
4. 后续应单独试验同项目多章节的证据选择、原文/整理副本的组合召回，以及岗位资料与五项卡片的事实绑定；使用新的独立问题及真实生成验收，而不是继续对这 172 题反复调参后宣称泛化改善。
