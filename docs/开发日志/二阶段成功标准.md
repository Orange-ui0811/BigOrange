## 3. 必须避免的回归问题

| # | 回归风险 | 预防措施 |
|---|---------|---------|
| R1 | API 路径变动导致 `test-frontend.html` 失效 | 二阶段所有 API 只新增不改名；如有必要改名，同步更新 test-frontend |
| R2 | 数据库表结构变更导致 Phase 1-7 业务逻辑异常 | `ALTER TABLE` 只加字段不删不改；新字段设 `DEFAULT` 值 |
| R3 | WebSocket 引入后原有 HTTP 聊天/通知接口失效 | 双通道并存：WebSocket 推送 + HTTP 查询兜底，互不影响 |
| R4 | 前端修改导致管理端和用户端鉴权逻辑混乱 | 两端独立部署，各自持有自己的 token，互不干扰 |
| R5 | Swagger 引入后拦截器放行缺失 | 新增拦截器排除 `/doc.html`、`/v3/**`、`/swagger-resources/**` |

## 6. 风险点与规避策略

| 风险 | 概率 | 影响 | 规避策略 |
|------|------|------|---------|
| **WebSocket 与 JWT 拦截器冲突** | 高 | 握手请求被 401 拦截 | WebSocket 路径 `/ws/**` 加入拦截器排除列表，鉴权通过 URL 参数传 token |
| **Element Plus 组件 API 变化** | 中 | 布局/表格/表单写法需要调整 | 二阶段开始前锁定 Element Plus 版本号，不追更 |
| **前后端分离导致 CORS 问题复现** | 中 | 管理后台 5173 端口跨域访问 8080 | 复用已有 CORS 配置，新增 `http://localhost:5173` 和 `http://localhost:5174` 到白名单 |
| **Redis 不可用导致 JWT 黑名单失效** | 低 | 退出登录后 token 仍可用 | Redis 连接失败时降级为允许访问（不阻塞正常业务），记录日志告警 |
| **统计 SQL 性能下降** | 低 | 数据量小时无影响，大时 `GROUP BY` 扫全表 | 统计加索引，仪表盘数据加 Redis 缓存 TTL=5 分钟 |
| **前端口径与后端 API 不一致** | 中 | 前端调的字段名不匹配后端返回 | 后端先出 Swagger JSON → 前端用工具自动生成 API 调用层 |

## 8. 需求与约束冲突时的升级沟通

如果中途发现以下情况：

| 情况 | 升级方式 |
|------|---------|
| **某 P0 任务依赖的技术栈不可用**（如 Element Plus 某个组件在当前版本有 bug） | 立即停止该任务 → 评估替代方案（换组件库 / 降级实现 / 手动写样式）→ 给出两种方案及各自代价 → 请你决策 |
| **前端实现中发现后端 API 返回数据不足以渲染页面** | 先在后端补齐缺失字段或新增轻度 API（不破坏现有结构）→ 记录变更 → 更新 Swagger → 继续前端 |
| **某个 P1 任务的实际工作量远超预估**（如 WebSocket 需要重写整个通知体系） | 给出"完整实现"和"MVP 实现"两种方案 → 标明各自的范围和代价 → 请你决策是否降级或延后 |
| **二阶段进行中突然需要修改一阶段 API 来支持新需求** | 评估影响范围（受影响的前端页面、test-frontend 按钮）→ 给出"最小改动"和"理想方案"→ 确认后再动手 |

**核心原则**：我不猜测你的意图。遇到选择题时，我给出选项、代价、影响范围，由你决定。
