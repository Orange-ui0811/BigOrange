## 2. 架构设计

### 2.1 岗位招聘全链路

```
                      ┌── 用户端 ──┐
                      │            │
              ┌───────┼────────┐   │
              ▼       ▼        ▼   ▼
        趋势分析页    投稿页   方案设计→岗位匹配
        工作能力参考  SubmitJob  PlanDesigner
              │       │        │   │
              ▼       ▼        ▼   ▼
         GET /app/job/*   POST /app/job/submit  POST /app/job/match
              │       │        │   │
              └───────┴────────┴───┘
                      │
                 job_posting 表
                      │
              ┌───────┴────────┐
              ▼                ▼
         用户投稿(PENDING)  管理员导入(APPROVED)
              │                │
              └───────┬────────┘
                      ▼
              管理员审核 JobAudit.vue
              │         │
        ┌─────┘         └─────┐
        ▼                      ▼
   POST /approve          POST /reject
        │
   ┌────┴────┐
   ▼         ▼
向量化入库  发50积分奖励
   │
   ▼
飞书通知(岗位专用webhook)
```

### 2.2 方案设计六阶段架构

```
Phase 1: 想法描述  ← 用户输入项目想法 + 补充信息 + 选择生成模式
Phase 2: 需求理解  ← AI 分析（40 segments/次）
Phase 3: 成功标准  ← AI 分析（40 segments/次）
Phase 4: 约束风险  ← AI 分析（40 segments/次）
Phase 5: 任务计划  ← AI 分析，支持精简模式（40 segments/次）
Phase 6: 岗位匹配  ← 向量检索 + AI 匹配（50 segments/次）
```

与旧版（四阶段）的核心变化：
- **Phase 1 不再是 AI 生成**，而是用户输入确认页，`generatePhase(1)` 直接保存内容到 `phases[0]`
- **Phase 6 单独路由**：`generatePhase(6)` → `doJobMatch()`，调用 `/app/job/match`，不走 `/app/plan/generate`
- **消费计费分层**：Phase 2-5 各 40 segments，Phase 6 单独弹窗 50 segments
- **记录存储扩展**：`plan_history` 表从 phase4 → phase6，`savePlan()` 和 `loadPlan()` 同步更新

### 2.3 飞书通知分流

| 审核类型 | Webhook URL 配置 | 用途 |
|---------|------------------|------|
| 作品审核（AI 托管） | `orange.feishu.webhook-url` | 用户提交作品 → AI 审核 → 飞书通知 |
| 岗位审核（手动） | `orange.feishu.job-webhook-url` | 用户投稿岗位 → 人工审核通过 → 飞书通知 |

配置读取方式：`@Value("${orange.feishu.job-webhook-url:}")`，默认空字符串（不发送通知）。

## 5. 关键设计细节

### 5.1 版权合规（避风港原则）

用户投稿岗位时必须勾选强制声明：
> 本人确认所提交的岗位信息来自公开渠道，不包含公司内部保密信息。

岗位详情页底部展示 DMCA 版权声明 + 联系邮箱 `orangejd2026@163.com`。

公司名处理策略：
- **管理员导入**：公司名存入 `content` 字段（完整保留），`displayContent` 自动剥离所有公司名（替换为"该公司"）
- **用户投稿**：`company` 字段固定为 `USER_SUBMIT`，JD 内容自动清洗已知公司名

### 5.2 岗位匹配（AI + 向量检索）

```
用户方案内容
    │
    ▼
VectorStore.similaritySearch(planContent, topK=5, threshold=0.5)
    │
    ▼
取 Top 5 岗位 JD（截断至300字）→ 拼入 prompt
    │
    ▼
DeepSeek V4 Pro 匹配 3 个最合适岗位
    │
    ▼
返回 JSON: { matches: [{ position, reason(100+字), focus(100+字) }] }
```

降级策略：
- `VectorStore == null`（Redis 不可用）：跳过检索，直接凭 AI 知识匹配
- AI 调用失败：自动退款 50 segments

### 5.3 方案设计 1-based 索引修复

Vue 3 template 中 refs 自动 unwrap，导致以下错误模式：

| 错误写法 | 后果 | 修复 |
|---------|------|------|
| `phases[currentPhase.value]` | NaN（数字 `.value` = undefined） | `phases[currentPhase-1]` |
| `generatePhase(0)` | 0 不是有效阶段 | `generatePhase(1)` |
| Phase API 参数 `phase: n` | 服务端索引差 1 | `phase: n-1` |
| `phases[4]` 映射岗位匹配 | 实际是任务计划 | `phases[4]` = 任务计划, `phases[5]` = 岗位匹配 |

最终索引映射：
```
phases[0] → Phase 1 想法描述 (用户输入)
phases[1] → Phase 2 需求理解 (AI)
phases[2] → Phase 3 成功标准 (AI)
phases[3] → Phase 4 约束风险 (AI)
phases[4] → Phase 5 任务计划 (AI)
phases[5] → Phase 6 岗位匹配 (AI + 向量)
```

### 5.4 导入去重修复

`AdminJobController.importJob()` 先删旧记录再插入，解决 `source_ref` 重复导致的 UNIQUE KEY 冲突：

```java
// AdminJobController.java line 87-93
// 删除旧记录避免 source_ref 重复
importJobPosting() 调用前先 delete 旧记录
```

### 5.5 飞书通知修复

岗位审核通过通知从 `sendWarning("AI审核异常")` 改为独立的 `sendAuditResult` 调用，使用绿色卡片模板 + "✅ 岗位审核通过" 标题。

## 6. 数据库

```sql
CREATE TABLE job_posting (
    id              BIGINT       NOT NULL AUTO_INCREMENT,
    company         VARCHAR(128) NOT NULL COMMENT '公司名（管理员导入存原名，用户投稿存USER_SUBMIT）',
    position        VARCHAR(256) NOT NULL COMMENT '岗位名称',
    direction       VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '技术方向',
    content         MEDIUMTEXT   NOT NULL COMMENT '原始JD内容（含公司名）',
    display_content MEDIUMTEXT   NOT NULL COMMENT '脱敏后展示内容（公司名替换为该公司）',
    audit_status    VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/APPROVED/REJECTED',
    submitter_id    BIGINT                COMMENT '投稿人 account.id',
    submitter_ip    VARCHAR(45)           COMMENT '投稿人 IP',
    submitter_role  VARCHAR(16)           COMMENT 'USER/ADMIN_IMPORT',
    reject_reason   VARCHAR(512)          COMMENT '拒绝原因',
    create_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_company_position (company, position),
    KEY idx_direction (direction),
    KEY idx_audit_status (audit_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='岗位招聘信息表';

-- plan_history 扩展
ALTER TABLE plan_history ADD COLUMN phase5 MEDIUMTEXT COMMENT '阶段5：任务计划';
ALTER TABLE plan_history ADD COLUMN phase6 MEDIUMTEXT COMMENT '阶段6：岗位匹配';
```

## 7. 已知问题

### 🟡 岗位匹配无检索结果时仍消耗配额

**现象**：Redis 不可用或知识库为空时，岗位匹配 AI 调用不包含任何参考 JD，但仍然消耗 50 segments。

**影响**：匹配结果质量下降，但不会报错。

**修复方向**：检测 `jobDocs.isEmpty()` 时给出提示并降低配额消耗。

### 🟡 精简模式只影响最终计划（Phase 5）

**现象**：`planMode='lite'` 仅在 `phase == 4`（即第五阶段任务计划）时生效，Phase 2-4 与详细模式完全相同。

**设计意图**：前三个阶段（需求理解/成功标准/约束风险）的分析质量不应因模式而降低，只有最终输出格式可精简。

### 🟡 岗位投稿查重仅按 position 匹配

**现象**：用户投稿复用 `company='USER_SUBMIT'` 查重，无法区分不同用户投同一公司同一岗位的情况。

**影响**：第二个用户投相同岗位会提示"可能已存在"。

**修复方向**：改为 (submitter_id, position) 联合查重或允许重复投稿后人工去重。
