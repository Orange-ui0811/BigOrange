## Phase 6: 交易闭环（优先级 7+8）

### Phase 6 前置说明：报价单与订单的关系

**订单有两种产生路径，报价单是路径之一而非唯一入口：**

```
路径 A（协商模式）：聊天 → 报价单 → 接受 → 自动生成订单
路径 B（直接购买）：作品详情 → 直接下单（适用于有固定价格售卖项的作品）
```

| 关键约定 | 说明 |
|----------|------|
| Quote 不强制先于 Order | 作品有明码标价的 `WorkSaleOption` 时，买家可直接创建订单 |
| Quote 服务于协商定价 | 定制需求、双方议价场景必须走报价单流程 |
| 两个模块代码独立 | Order 通过 `source_type`（QUOTE / WORK）+ `source_id` 记录来源 |
| 订单状态机统一 | 无论来源路径，进入 Order 后状态机相同 |

### Step 6.1 — Quote + Order + PaymentStage + Delivery 建表

**输入**：§6.12、§6.13、§6.14、§6.15  
**产出物**：4 张表 + Entity/Mapper

- `PUT /app/quote/{id}/reject` — 拒绝报价
- `GET /app/quote/{id}` — 查看报价详情

**状态流**：`PENDING_CONFIRM → ACCEPTED / REJECTED / CANCELLED / EXPIRED`

### Step 6.3 — 订单模块

**产出物**：
- `POST /app/order` — 创建订单（报价单被接受后自动创建 或 直接购买作品）
- `GET /app/order/{id}` — 订单详情
- `GET /app/order/buy` — 我的买入
- `GET /app/order/sell` — 我的卖出/接单
- `PUT /app/order/{id}/deposit` — 支付定金标记
- `PUT /app/order/{id}/deliver` — 提交交付
- `PUT /app/order/{id}/confirm` — 确认交付
- `PUT /app/order/{id}/final-pay` — 支付尾款标记

**订单状态机**（§7.5）：
```
CREATED → WAITING_DEPOSIT → DEPOSIT_PAID → IN_PROGRESS
  → WAITING_FINAL_PAYMENT → FINAL_PAID → DELIVERED → COMPLETED
  ↓ 任何异常
  CANCELLED / DISPUTED
```

## 3. 全局技术约定

### 3.1 包结构约定（每个业务模块保持一致）

```
com.orangejd.server
├── controller
│   ├── admin/          # 管理端接口（需 Admin JWT）
│   └── app/            # 用户端接口（需 App JWT）
├── service/            # 接口定义
├── service/impl/       # 实现
├── mapper/             # MyBatis Mapper 接口
└── task/               # 定时任务
```

### 3.2 数据层约定

#### 基础字段
- Entity 继承 `BaseEntity`（含 createTime/updateTime，由 AutoFill 切面自动填充）
- 所有表必须有 `id`（自增 BIGINT）、`create_time`、`update_time`

#### 金额字段（交易属性项目，强制）
- **所有金额字段统一使用 `DECIMAL(12,2)`**，禁止 `float` / `double`
- 涉及字段：`WorkSaleOption.price`、`Requirement.budget_min`、`Requirement.budget_max`、`Quote.price`、`Order.deposit`、`Order.final_amount`、`Order.total_amount`
- 原因：浮点数存在 IEEE 754 精度丢失，交易场景不可接受；`DECIMAL(12,2)` 支持最大 9,999,999,999.99 元，足够覆盖

#### 状态字段
- 所有状态字段使用 `VARCHAR` 存枚举字符串（如 `'PENDING_REVIEW'`、`'APPROVED'`）
- 不写死数字（如 0/1/2），方便 SQL 调试、可读性和跨语言对接

#### 外键命名
- 所有外键字段统一 `xxx_id` 格式：`owner_id`、`category_id`、`work_id`、`buyer_id`、`seller_id`、`auditor_id`、`conversation_id`

#### 索引策略
- 以下核心查询字段必须建索引（在 `schema-v1.sql` 中一并设计）：

| 维度 | 索引字段 |
|------|---------|
| 用户维度 | `owner_id`、`publisher_id`、`account_id`、`buyer_id`、`seller_id` |
| 审核维度 | `audit_status`、`visibility_status` |
| 分类维度 | `category_id` |
| 订单维度 | `order_status` |
| 关联维度 | `work_id`、`requirement_id`、`conversation_id` |

#### 逻辑删除
- **第一阶段不引入逻辑删除**（`deleted` / `is_deleted` 字段）
- 理由：MVP 数据量小，物理删除简单直接；后续若需数据恢复，统一加 `is_deleted` + `deleted_at` 两个字段
- 涉及删除的 Controller 必须在 Service 层校验权限（仅本人可删）

### 3.3 API 约定

- 统一前缀：管理端 `/admin/*`，用户端 `/app/*`
- 统一返回：`Result<T>`（code=1 成功，code=0 失败）
- 分页返回：`PageResult<T>`（total + records）
- 异常统一由 `GlobalExceptionHandler` 处理

### 3.4 鉴权约定

- 管理员接口 → `JwtTokenAdminInterceptor` 校验
- 用户端接口 → `JwtTokenAppInterceptor` 校验
- Controller 方法中通过 `BaseContext.getCurrentId()` 获取当前用户 ID

### 3.5 代码构建顺序约定

每个业务模块严格按自底向上顺序构建（先数据后逻辑，不可跳跃）：

```
① SQL 建表      →  表结构落地
② Entity/DTO/VO →  数据对象定义
③ Mapper + XML  →  数据访问层
④ Service       →  业务逻辑层
⑤ Controller    →  接口暴露层
⑥ 验证          →  端到端调用确认
```

**原则**：
- 不跳跃：Mapper 未就绪时不写 Service，Service 未就绪时不写 Controller
- 每层可独立单测：Mapper 用 MyBatis 测试，Service 用 Mock，Controller 用 HTTP 请求
- 同层并行：Entity/DTO/VO 可并行编写；同一 Phase 内多个模块的 Mapper 可并行

> 每个 Phase 内的 Step 编号即对应此顺序（Step X.1 建表 → Step X.2 Entity/DTO → Step X.3 Mapper → Step X.4 Service → Step X.5 Controller → Step X.6 验证）。

### 3.6 数据权限约定

本项目多角色（管理员 / 创作者 / 需求方 / 买家 / 卖家），数据权限规则必须在每层落实。

**数据可见性矩阵：**

| 角色 | 数据范围 | 规则 |
|------|---------|------|
| 匿名/未登录 | 公开市场 | 只能看到 `audit_status=APPROVED` + `visibility_status=PUBLIC` 的内容 |
| 普通用户 | 公开市场 | 同上 |
| 普通用户 | 本人数据 | 只能编辑自己的作品/需求/个人资料 |
| 普通用户 | 参与方数据 | 只能查看自己参与的会话、报价单、订单 |
| 管理员 | 全部数据 | 可查看/管理所有用户、内容、订单（路径 `/admin/*`） |

**Service 层强制权限规则**（每条对应用户端一个校验点）：

| # | 规则 | 适用模块 | 校验方式 |
|---|------|---------|---------|
| 1 | 非作者不能编辑/删除作品 | Work | `owner_id == currentId()` |
| 2 | 非发布者不能编辑需求 | Requirement | `publisher_id == currentId()` |
| 3 | 非会话参与方不能查看消息 | Conversation / Message | `buyer_id \|\| seller_id` |
| 4 | **非报价接收方不能接受/拒绝报价** | Quote | `receiver_id == currentId()` |
| 5 | **非订单参与方不能查看订单详情** | Order | `buyer_id \|\| seller_id` |
| 6 | 市场接口仅返回已审核公开内容 | Market | SQL `WHERE audit_status='APPROVED' AND visibility_status='PUBLIC'` |
| 7 | `/my` 接口仅返回当前用户数据 | Work / Requirement | SQL `WHERE owner_id = #{currentId}` |

**实现方式**：
- `/admin/*` 不做数据范围限制（管理员全量访问）
- 用户端在 Service 层通过 `BaseContext.getCurrentId()` 与数据属主字段比较
- 市场查询类接口在 Mapper XML 中直接加 `WHERE` 条件（防漏）
- 权限校验失败统一抛出 `BaseException("无权限")`，由 `GlobalExceptionHandler` 转为 HTTP 403

### 3.7 文件上传策略预留

**第一阶段不引入完整文件系统，但架构层面做好隔离，避免后续返工。**

| 决策 | 说明 |
|------|------|
| MVP 方案 | 所有文件字段先存 URL 字符串（`cover_url`、`avatar_url`、`demo_url`、`attachment_url`） |
| 上传入口 | 统一放在 `orange-common` 模块的 `FileUploadService`（接口），当前返回占位 URL |
| 各模块不自行处理上传 | Work / Profile / Message 等模块只存 URL，通过 `FileUploadService` 获取 |
| 存储后端预留 | 骨架已有 `OssProperties` 配置类，第二阶段切换 OSS 时只改 `FileUploadService` 实现 |
| 涉及字段 | `Work.cover_url`、`Work.demo_url`、`UserProfile.avatar_url`、`Message.attachment_url` |

> 第二阶段统一替换上传实现时，各业务模块零改动——只换 `FileUploadService` 的实现即可。

## 5. 测试策略与交付物模板

### 5.1 三层验证体系

每个 Phase 从三个层次独立验证，每层有自己的关注点：

| 层次 | 验证目标 | 工具 |
|------|---------|------|
| Mapper 层 | SQL 正确性、索引命中、CRUD 行为 | MyBatis Test + H2 / MySQL |
| Service 层 | 业务逻辑、状态流转、异常分支、权限校验 | JUnit + Mockito |
| Controller 层 | 鉴权、参数校验、HTTP 状态码、返回格式 | Postman / curl |

**原则：先验证失败场景，再验证成功路径。** 失败场景是后续改动的保护网——成功路径可能在错误实现下也能"碰巧"通过，失败场景能真正拦住回归。

### 5.2 每个 Phase 最低失败场景覆盖

每个 Phase 至少覆盖以下场景，确保反向校验到位：

| Phase | 必须覆盖的失败场景 |
|-------|-------------------|
| Phase 1 | ① 错误密码登录返回统一错误响应（非 500） ② App token 访问 `/admin/*` 被 403 拒绝 ③ 重复用户名注册被拦截 ④ 旧密码错误时修改密码失败 |
| Phase 2 | ① 非管理员创建/编辑分类被拒绝 ② 停用的分类在用户端不可见 ③ 已关联内容的分类不可删除（或提示） |
| Phase 3 | ① **未审核（PENDING_REVIEW / DRAFT）内容不在市场展示** ② 非作者不能编辑/删除作品 ③ 已审核内容也可删除或设为私密 ④ 重复提交审核被拦截 |
| Phase 4 | ① 私有/未审核作品不在市场列表出现 ② 重复收藏不产生脏数据（唯一约束） ③ 空评论/超长评论被拦截 ④ 非本人不能查看他人收藏夹 |
| Phase 5 | ① **非参与方不能查看会话和消息** ② 向自己发起会话被拦截 ③ 通知不可被他人标记已读 ④ 未登录不能建立 WebSocket 连接 |
| Phase 6 | ① **非报价接收方不能接受/拒绝报价** ② **非订单参与方不能查看订单详情** ③ 状态不匹配的操作被拒绝（如已取消订单不可支付、未付定金不可交付） ④ 直接下单金额与 WorkSaleOption 不一致时告警 |
| Phase 7 | ① App 用户访问 `/admin/*` 全部被拦截 ② 统计数据仅管理员账号可见 ③ 管理员不能删除处于进行中状态的订单 |

### 5.3 交付物模板

每个 Step 完成后，应产出以下可验证物：

| 层次 | 交付物 | 验证方式 |
|------|--------|---------|
| 数据层 | 建表SQL + Entity + Mapper + XML | 单元测试 Mapper 方法 |
| 业务层 | Service 接口 + ServiceImpl | 单元测试 Service 方法（含失败分支） |
| 接口层 | Controller | Postman/curl 调用验证（含失败场景） |
| 集成 | — | 完整链路调用通过 |
