# 平台项目设计

## 1. 平台定位

本平台是一个面向 vibe coding 创作者与需求方的数字产品展示、交易和定制撮合平台。

它可以理解为“咸鱼 + 作品集 + 定制开发接单平台”的结合体。用户不是固定买家或卖家，而是同一账号在不同场景下切换身份：

- 当他发布作品时，他是创作者/卖家。
- 当他购买作品时，他是购买方。
- 当他发布需求时，他是需求方。
- 当他承接需求时，他是接单方。
- 当他审核内容时，他是管理员。

平台主要有两条交易主线：

- 作品交易：用户发布自己做的 vibe coding 产品，审核通过后公开展示。其他用户可以购买源码、使用权、部署服务，或组合购买。
- 定制需求：用户发布需求和预算范围，审核通过后展示。其他用户可以沟通、报价、达成合作。正式交易采用定金 + 尾款的阶段模式。

第一阶段要优先跑通这条核心闭环：

```text
注册登录
发布作品/需求
平台审核
公开展示
搜索浏览
收藏评论
发起聊天
协商报价
确认订单
支付定金标记
交付
支付尾款标记
订单完成
```

## 2. 第一阶段成功标准

第一阶段成功，不是功能很多，而是要证明平台的核心交易逻辑成立。

建议成功标准如下：

- 用户可以注册登录，并拥有统一账号身份。
- 用户可以发布作品，作品审核通过后能在作品市场展示。
- 用户可以发布需求，需求审核通过后能在需求广场展示。
- 用户可以搜索、筛选、查看作品和需求详情。
- 用户可以收藏、评论作品或需求。
- 用户可以通过“想要/联系”进入聊天，完成初步沟通。
- 双方可以基于聊天创建报价单/交易方案。
- 报价单确认后可以生成订单。
- 定制订单支持定金、尾款两个阶段的状态流转。
- 管理员可以审核作品、审核需求、查看用户和订单。
- 系统核心对象和状态设计不写死，为后续接真实支付、争议处理、评价体系、部署交付服务预留空间。

阶段验收指标：

- 一个新用户能完整发布一个作品并通过审核展示。
- 一个需求方能发布需求并通过审核展示。
- 两个用户能通过聊天达成报价并生成订单。
- 一个定制订单能从待付定金流转到进行中，再到待付尾款，最后到已完成。
- 管理员能对作品和需求做审核处理。

## 4. MVP 明确不做

第一阶段明确不做以下内容，避免范围过大：

- 不接真实支付网关，先做支付状态标记和订单模型。
- 不做平台担保交易、自动分账、提现。
- 不做复杂退款、仲裁、争议流程，只预留状态。
- 不做完整 IM，只做基础文本聊天。
- 不做语音、视频、文件大附件传输。
- 不做复杂推荐算法，先做搜索、分类、排序。
- 不做复杂信用体系，先预留评分和评价。
- 不做企业认证、实名认证。
- 不做多租户 SaaS。
- 不做自动部署服务，只在作品售卖项里预留“部署服务”类型。
- 不做复杂权限系统，先做普通账号和管理员两类权限。
- 不做移动端 App，先按 Web/管理后台优先。

## 5. 核心角色流程

### 5.1 作品交易流程

```text
用户注册登录
完善个人资料
发布作品
提交审核
管理员审核通过
作品进入市场展示
其他用户搜索/查看作品
点击想要
进入聊天
选择购买源码/使用权/部署服务
生成作品订单
支付状态标记
交付资料
订单完成
```

### 5.2 定制需求流程

```text
用户注册登录
发布需求和预算范围
提交审核
管理员审核通过
需求进入需求广场
创作者查看需求
点击想要/联系
进入聊天沟通
创作者发起报价单
需求方确认报价单
生成定制订单
需求方支付定金
创作者开始开发
创作者提交交付
需求方确认
需求方支付尾款
订单完成
```

### 5.3 管理员审核治理流程

```text
管理员登录
查看待审核作品/需求
查看详情与用户信息
通过或拒绝
系统通知发布者
审核通过后公开展示
后续可下架违规内容
可查看订单和评论
```

## 8. 后端业务域拆分

基于当前 Java 骨架，建议后端按以下业务域拆分：

### 8.1 auth

登录、注册、JWT、密码修改。

### 8.2 account

账号资料、头像、个人主页、身份标签。

### 8.3 market

首页搜索、作品/需求聚合浏览、筛选排序。

### 8.4 work

作品发布、作品编辑、作品详情、售卖项、上下架。

### 8.5 requirement

需求发布、需求编辑、需求详情、需求状态。

### 8.6 interaction

收藏、评论、浏览历史。

### 8.7 message

会话、私信、系统通知、审核通知、订单通知。

### 8.8 quote

报价单、交易方案、协商确认。

### 8.9 order

作品订单、定制订单、定金尾款、履约状态。

### 8.10 audit

作品审核、需求审核、审核记录。

### 8.11 admin

管理端用户管理、内容管理、订单查看、分类标签管理。

### 8.12 category

作品/需求分类、标签体系。

### 8.13 report

平台统计、管理后台仪表盘、后续报表导出。

## 9. 第一阶段优先级

建议第一阶段按以下顺序落地：

1. 账号与个人资料
2. 作品/需求发布与审核
3. 首页浏览、搜索、详情
4. 收藏、评论、浏览历史
5. 聊天与通知
6. 报价单
7. 订单与定金/尾款状态
8. 管理端审核与基础治理
9. 统计仪表盘

这条路线的核心是：先让内容能产生，再让内容能展示，再让人能沟通，最后让沟通能形成订单。

## 10. 一句话收束

这个 MVP 的成功，不是马上做成完整交易平台，而是跑通：

```text
发布内容 -> 审核展示 -> 沟通协商 -> 报价确认 -> 阶段订单 -> 完成交付
```

同时，要把支付、争议、评价、部署服务这些未来能力的位置留好。
